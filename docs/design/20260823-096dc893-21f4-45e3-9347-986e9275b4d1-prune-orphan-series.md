# DSG-096dc893-21f4-45e3-9347-986e9275b4d1: prune を paths の列挙・engine の判定と削除・CLI の同意解釈に分け、engine API を Reset と同型にする

## 設計

`nput prune` を 3 層に分ける。既存コマンドと同じ層境界（→ DSG-7d354fe0-a333-495b-9f4b-14bba316dc47）に
乗せ、prune 専用の縦割りを作らない。

```
internal/paths/    ← roothash 系列の列挙と backref の読み取り。ListRootHashSeries / ReadBackref
internal/engine/   ← root 実在の判定・try-lock・系列の順序付き削除。Prune / PruneOptions / PruneResult
cmd/nput/          ← TTY 判定・--yes・--json の解釈と、確認プロンプトの提示
```

**`internal/paths`** はプロファイルレイアウトの計算を既に持つ層で（`Resolve` / `Base` /
`RootHash`）、`<roothash>` 階層の形と backref `.root` の位置を知っているのはここだけ。列挙
（`ListRootHashSeries`）と backref 読み取り（`ReadBackref`）をここへ置くと、レイアウトの知識が
1 箇所に留まる。この 2 関数は prune 専用ではなく、`nput status`（→ #198）が同じ列挙を使う。

この配置は `internal/paths` の性格を変える。TP-e7c25263-6d2d-4a37-8275-26906889d912 は同
パッケージを「FS に一切触れずに判断する層」（state ディレクトリ・世代パスの解決・root の
ハッシュ化）として名指しし、入力が列挙可能だから table-driven のユニットで覆えと規範化して
いるが、`ListRootHashSeries` はディレクトリを走査し `ReadBackref` はファイルを読む。**この
2 関数は同 TP の言う純ロジック層の例外**であり、入力が FS の状態である以上 table では覆えない。
既存の純関数（`Resolve` / `Base` / `RootHash` / `GenerationLink`）はこれまでどおりユニットの
table で覆い、新設 2 関数は tmpdir を張った実 FS の統合レベルで覆う（同 TP が engine に対して
定める主戦力と同じ層）。

`internal/planner` は同じ問題を FS の注入（`FS` interface + fake）で解いており
（→ DSG-8b96869c-842e-4f78-8ff7-df1f1d6c1a68）、こちらはそれを採らない。planner が読むのは
「この 1 パスが symlink か・リンク先が記録どおりか」という個別の問い合わせで fake に置き換えて
も検証対象が残るのに対し、`ListRootHashSeries` が検証したいのは **`Base` 直下に実際に並んだ
レイアウトそのもの**（`.root` を持つ dir と持たない dir が混在した木を正しく振り分けられるか）
で、fake FS で作った木は「fake がそう並べたこと」しか確かめない。この違いがあるので、prune の
列挙は実 FS の tmpdir で覆う。

**`internal/engine`** が root の実在判定・lock・削除を持つ。FS 意味論の実行は engine の担当で
（→ DSG-8b96869c-842e-4f78-8ff7-df1f1d6c1a68）、prune もその例外にしない。

**`cmd/nput`** は TTY 判定と `--yes` / `--json` の解釈だけを持つ。engine が見るのは `Confirm`
コールバックの戻り値までで、同意をどう取ったかは知らない（`reset` と同じ分担）。

### engine API は Reset と同型

```go
type PruneOptions struct {
    StateDir  string // <state>。paths.Base() を通して基底になる（空なら paths.StateDir() で解決）
    SystemDir string // 完成した基底そのもの。Base() を通さない（空なら /nix/var/nix/profiles/nput）
    DryRun    bool
    Confirm   func(*PruneResult) (bool, error)
    Warnf     func(format string, args ...any)
}

func Prune(opts PruneOptions) (*PruneResult, error)
```

`ResetOptions` の `DryRun` / `Confirm` / `Warnf` をそのままの意味で持つ（→ `internal/engine/reset.go`）。
共有する 3 つのうち 1 点だけ意味が違うのは、**`Confirm` へ渡すのが戻り値そのものではなく判定結果の
preview** である点。`Reset` は `res` 自身をコールバックへ渡すので `Aborted` はコールバックが見た
オブジェクトに立つが、prune の `Removed` は削除段を経て「実際に削除した系列」の意味になるため、
同じオブジェクトを渡すと CLI が表示用に握った候補一覧が後から空になる。preview を別値にして、
`Aborted` は戻り値の側だけに立てる。

もう 1 つの違いはフィールド集合の側で、prune が config を名指ししないため
`Name` / `RootKind` / `WorkDir` / `Git` を持たず、入力が走査基底の 2 つだけになる。entrypoint
発見も nix eval / build も行わない。

**基底を 2 つ受けるのは REQ-c44433a1-7ee7-459a-9aae-7cc42166876f が走査対象に system 基底を
含めるため**（→ ADR-0036 §3）。`SystemDir` を定数の直書きにせずフィールドで受けるのは、
tmpdir に張った偽の system 基底を差し込めないとテストが実 `/nix/var/nix/profiles/` を触ることに
なるため。CLI は既定値のまま渡し、テストだけが上書きする。

2 つのフィールドは**指す階層が違う**。`StateDir` は `<state>` で、engine が `paths.Base()` を
通して基底 `<state>/nix/profiles/nput` を得る（既存コマンドが `paths.StateDir()` の結果を渡す
のと同じ値）。`SystemDir` は `paths.Base()` を通さない完成した基底そのもので、system mode の
profile 基底が `nix/profiles/nput` を挟まないレイアウトだから（→ ADR-0036 §3）。取り違えると
`/nix/var/nix/profiles/nput/nix/profiles/nput` を走査することになるので、フィールドのコメントで
区別を明示する。

### 基底が無いのは正常、読めないのは報告する

2 つの基底を常に走査するが、**基底自体が存在しないのは正常系**として扱い、その基底の孤児 0 件と
みなして続ける。system mode を一度も使っていない環境では `/nix/var/nix/profiles/nput` が無いのが
普通で、これを毎回 warning にすると意味のない出力が定常的に出る。

一方、**基底が存在するのに読めない**（権限等で `ReadDir` が失敗する）ときは、`Warnf` でその基底を
名指しして報告し、もう一方の基底の処理は続ける。系列単位の `Skipped` には載せない（どの系列が
あったのか分からないので載せようがない）。この区別が無いと、非 root 実行で system 基底が読めない
状況が「孤児 0 件で正常終了」と見分けられなくなる（→ RISK-f522a51b-db4b-4164-bd20-63fa4a0cb27d）。

`DryRun` は列挙と判定だけを行い、lock も取らず FS を変えない。`Confirm` は非 nil のときだけ
呼ばれ、削除直前に**判定済みの preview**（前掲のとおり戻り値とは別値）を渡す。root パス一覧が
ここに入っているので、CLI はそれを表示する。false を返したら削除せず `Aborted` を立てて返る
——立つのは戻り値の側で、コールバックが握った preview には立たない。

```go
type PruneResult struct {
    Removed []PruneSeries  // 削除した（dryrun では削除予定の）系列
    Skipped []PruneSkipped // 対象外にした系列と理由
    DryRun  bool
    Aborted bool
}

type PruneSeries struct {
    RootHash string   // <roothash>（系列ディレクトリ名）
    Root     string   // backref .root が記録する root の絶対パス
    Names    []string // 配下の <name> profile
    Dir      string   // 系列ディレクトリの絶対パス（どちらの基底の系列かを持つ唯一のフィールド）
}

type PruneSkipped struct {
    Series PruneSeries
    Reason PruneSkipReason
    Detail string
}
```

`PruneSeries` の `RootHash` / `Root` / `Names` は、REQ-42fe312c-927c-4da3-9346-f7ca2f3a58ed が
`--dryrun` の出力項目として挙げる `<roothash>` / root パス / 配下 `<name>` 一覧と 1:1 で対応する。
`Confirm` に渡す `PruneResult` にも同じものが入るので、CLI は削除前の root パス一覧をこの `Root`
から組み立てる。

**`Dir` は系列がどちらの基底から来たかを持つ唯一のフィールド**。`<roothash>` は root パスの
ハッシュ（→ `paths.RootHash`）なので、同じ root を project mode と system mode の `--root` 明示で
使えば**両方の基底に同名のディレクトリが立つ**。`Dir` が無いと、`Removed` の 1 行も warning も
どちらの系列を指すのか言えなくなる。系列を名指しする warning とエラーはこの `Dir` を使う。

`PruneSkipReason` は `"locked"` / `"backref-unreadable"` / `"series-unreadable"` /
`"root-stat-failed"` / `"permission-denied"` の 5 値。判定材料が欠けた系列と、削除する権限が
無い系列を黙って落とさず、理由付きで返す（→ REQ-c44433a1-7ee7-459a-9aae-7cc42166876f の
「安全側へ倒す」）。root が実在していて対象外になった系列は失敗ではないので `Skipped` に
入れない。

`series-unreadable` は `ListRootHashSeries` が `NamesErr` を載せて返した系列に対応する
（→ `internal/paths`）。backref は読めたので root パスは決まるが、配下の `<name>` profileDir が
列挙できていないので、**lock すべき鍵の集合も削除すべき実体の集合も分からない**。`Names` が
nil であることは「`<name>` を持たない系列」と見分けが付かず（`NamesErr` を見ないと区別できない）、
これを `.root` 単独の系列として扱うと lock なしで削除する経路へ落ちる。判定材料が欠けた系列を
削除へ倒さない規律は backref 側と同じなので、独立した理由として `Skipped` へ載せる。

**`Skipped` に入る全ケースで `Warnf` を呼ぶ。** 5 値のいずれであっても、系列を残した理由は
warning として出す。`Skipped` に構造化して返すのは CLI がまとめて扱うためで、`locked` だけ
warning・判定不能系は黙殺、という不揃いは REQ-c44433a1-7ee7-459a-9aae-7cc42166876f の
「その理由を warning として報告しなければならない」に反する。

**skip できるのは「何も消えていない × 権限」だけ。** 削除は `<name>` 単位のループなので、失敗は
系列の途中でも起きる。**そこまでに何か消えたか**と**理由が権限か**の 2 軸で 4 通りあり、
`Skipped` へ倒せるのはその 1 つだけ。上位の規範は 2 件に分かれていて、着手前の権限失敗を
「残す」側に入れるのが REQ-c44433a1-7ee7-459a-9aae-7cc42166876f、着手後の失敗をエラーとして
報告するのが REQ-42fe312c-927c-4da3-9346-f7ca2f3a58ed。本節はその境目を実装の分岐へ落とす。

| | 権限（`fs.ErrPermission`）| 権限以外（EBUSY・read-only FS・I/O）|
|---|---|---|
| **何も消えていない** | `Skipped{permission-denied}`・続行 | エラー・中断 |
| **1 つ以上消した** | エラー・中断 | エラー・中断 |

4 セルのうち**「何も消えていない × 権限以外」だけは直接の検証を持たない**。削除の最初の一手は
列挙が実在を確認した `<name>` ディレクトリの unlink で、そこを静的な fixture から非権限の errno で
落とす手が無い（ENOTDIR / ENOTEMPTY はいずれも `.root` 削除後にしか現れず、`.root` を非空
ディレクトリにする案は `ReadBackref` が先に落ちて `backref-unreadable` になる）。実装へフォールト
注入の seam を足す選択は採らないので、このセルは規範として残しつつ検証は
TC-a9857bf7-f7f9-41f9-b42c-9993fd16a5e9 が定める代替（非権限の失敗が `permission-denied` へ
丸められないことと、権限側の 2 セルの対）で担保する。

- **何も消えていない × 権限** — その系列はまだ手付かずで、かつ「消せない環境で実行された」だけ
  なので `Skipped` へ倒し、他の基底・他の系列の削除は続ける
  （→ ADR-0036 §3「非 root 実行の prune は権限エラーの系列を warning 付きで skip する」）。
  非 root で system 基底の孤児系列を消そうとすれば最初の `RemoveAll` が `fs.ErrPermission` で
  落ちるので、ADR-0036 §3 が想定する状況はここに落ちる
- **何も消えていない × 権限以外** — 手付かずではあるが、権限を上げれば消えるとは限らない
  （read-only FS はそもそも消せない）。`permission-denied` へ丸めると「権限を直せば消える」と
  読める誤った案内になるので、エラーで返す。`Skipped` に受け皿となる理由を足さないのは、
  prune が意味のある案内を出せる skip 理由は権限だけだから
- **1 つ以上消した**（理由を問わず）— `Skipped` にはしない。その系列は「残した」のではなく半端に
  壊れているので、`Removed` にも数えず、系列を特定できる形でエラーを返して後続の系列へは進まない
  （`Removed` には失敗より前に**完了した**系列だけが入る）

`Skipped` を「手を付けなかった系列」の意味に保つのがこの境目の目的で、系列単位 all-or-nothing で
lock を取る理由（後述）と同じ考え方に立つ。実装が持つのは**その系列で 1 つでも削除が完了したかの
状態**で、まずそれを見て skip 可能かを決め、可能な場合にだけ `errors.Is(err, fs.ErrPermission)` で
理由を確かめる。削除前に書き込み可否を先に確かめる事前判定は採らない（TOCTOU になり、判定と実行で
2 つの真実を持つ）。

**削除は `<name>` から始め `.root` を最後に消す。** `.root` が先に消えると、以後その系列は走査
対象から外れて prune でも手動でも辿れなくなる。`os.RemoveAll(<roothash>)` の一発は子の削除順を
呼び出し側から指定できない（`ReadDir` が返した順に消す）ので使わない。配下の
`<name>` を 1 つずつ `RemoveAll` し、最後に `.root` を消してから `<roothash>` を `Remove`
（空 dir の rmdir）する。途中で失敗しても `.root` が残るので、次回の実行が同じ系列をふたたび
拾える。

**フィールド名に `Pruned` を使わない。** `Result.Pruned` が既に「除去後に rmdir した空祖先
ディレクトリ」の意味で埋まっており（→ REQ-8409db86-a1ba-4053-86dc-588985cc1ca7）、prune の
削除系列を同じ語で呼ぶと同じ構造体群の中で 2 つの意味が衝突する。削除した系列は `Removed`。

### root の判定条件は 1 つだけ

判定は 2 段。**前段が backref の妥当性検査**で、`ReadBackref` が返した値が読めない・空・絶対
パスでないのいずれかなら、root パスが決まらないので `backref-unreadable` で skip する
（`filepath.IsAbs` で弾く。ここで弾かないと相対パスが `os.Stat` の cwd 相対解決に流れ、無関係な
パスの実在で判定が決まる）。`ReadBackref` は読んだ内容の前後の空白・改行を落としてから返す
（`.root` をファイルとして書く以上、末尾改行の有無で判定が変わってはならない）。

前段を通った root について、**後段は `os.Stat(root)` の 1 条件**。`fs.ErrNotExist` のときにだけ
孤児と判定し、`nil` は生存、それ以外のエラーは判定不能として `root-stat-failed` で skip する。
この 2 段を通って孤児と決まった系列には、削除の直前にもう 1 つ門がある。**`NamesErr` が
載っている系列は `series-unreadable` で skip する**（前々節）。判定は済んでいるが削除する実体の
集合が分からないので、判定材料の欠落と同じく残す側へ倒す。

条件を 1 つに保つことで、判定材料が欠けたときに削除へ倒れる経路が構造的に生じない。`os.Stat` は
symlink を辿るので、dangling symlink の root は追加の分岐なしに不在として落ちる。root だった
パスがファイルに置き換わっていれば `nil` が返って生存側に落ちるが、これは意図した帰結（条件は
「実在しない」だけで、種別は見ない）。

### lock 規律

系列の削除前に、その系列内の**全 `<name>` profileDir** を try-lock で取る（lock の鍵は
profileDir 単位 → `internal/lock`）。

- 1 つでも `ErrLocked` なら**系列ごと skip**（`locked`）。既に取れていた分は即 `Release` する
- `ErrLocked` 以外の `Acquire` エラーも同じく skip + warning（判定不能を削除へ倒さない）
- 全部取れたら**保持したまま**系列を削除し（`<name>` → `.root` → `<roothash>` の順・前節）、
  その後 `Release` する。削除の最中に他プロセスが同じ profileDir の lock を取れないことが、
  保持したまま消す理由
- `<name>` を 1 つも持たない `.root` だけの系列は、lock の鍵になる profileDir が無いので lock
  なしで削除する。**この経路へ入れるのは `NamesErr == nil` かつ `Names` が空のときだけ**で、
  `Names == nil` を条件にしてはならない。列挙に失敗した系列も `Names` は nil で返るため
  （→ `internal/paths` の `RootHashSeries`）、nil だけを見ると「鍵が無い」と「鍵が分からない」が
  同じ経路へ落ち、lock すべき profileDir を素通りして削除する。`NamesErr != nil` の系列は
  そもそも削除せず `series-unreadable` で skip する（前節）ので、lock なし削除に到達しない

系列単位で all-or-nothing にするのは、`<roothash>` ごと消す削除単位に lock の粒度を合わせる
ため。一部の `<name>` だけ lock を取って部分削除すると、生きている `<name>` を持つ系列が
半端に壊れる。

### 世代を持たない系列も対象

`.pending` と `.root` だけがあり世代リンクが 1 つも無い系列も、root 不在なら削除する。実機の
孤児 95 件のうち 54 件がこの形で（開発者環境での実測・2026-08-23 の Issue #127 分割時点）、
「世代がある系列」に限ると過半が残る。列挙は `.root` の有無で行い、世代の有無を条件にしない。

### この設計が引き受ける代償

判定ロジックが新規で、既存の配置系ゲート（planner の分類・stale 除去の保守的不変条件）の
どれにも乗らない（→ RISK-f522a51b-db4b-4164-bd20-63fa4a0cb27d）。安全機構の側は `reset` の
確認・dryrun 経路と同型にすることで既存のテストと規律に乗せているが、乗り切らない分は
残る（→ RISK-0909e121-8ec4-40c8-ab1c-562e61f31067）。
