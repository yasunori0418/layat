# リスク（`risk`）

* [copy が place-once を破り、ユーザーのローカル編集を失わせる](./20260809-01cf9f47-95bd-419a-863d-0d7c1f8188ba-copy-destroys-local-edits.md) - copy は「target 不在のときにだけマテリアライズし、以後は触らない」という place-once の契約で成り立っている。ユーザーは配置後のファイルを自分で編集する前提で copy を選ぶため、再 apply が利用者に知らせずに上書きすればその編集は復元手段なく失われる。copy は世代管理の対象外なのでロールバックでも戻せない。
* [engine の実行結果から JSON ペイロードへの写像が実際に起きたことと食い違う](./20260809-06d7375e-fecd-4a0a-9ceb-1f9e207c3308-engine-result-mapping.md) - schema に適合していても、その文書が述べている内容が実行の事実と食い違えば、消費側は「正しい形式で嘘をつかれる」ことになる。適合チェッカはエンベロープの形しか見ないため、この層は写像そのものを検証しない限り守れない。
* [評価時に止めるべき入力が止まらずに engine 実行時まで到達する](./20260809-09df40d3-2752-433e-9ab0-2816fbd14969-eval-gate-bypass.md) - `mkManifest` は `evalModules` で入力を確認する単一の箇所（REQ-d1b5b3f5-10a0-400d-9f03-ba00c63d1c34）で、パス安全性（REQ-6911eab6-12b4-457c-9db4-d7430a9e9b3f）・未知キーと旧名の拒否（REQ-3e446ad9-a6f4-4229-b5c5-184754b0ef51）・entry のフィールドを 4 つに限ること（REQ-a33a11e3-830d-4142-88ed-4c1fc35e7f74）・意図が矛盾する組み合わせ（REQ-16faf428-77f3-492f-b858-222c5274cbf7）・同一 manifest 内の target 衝突（REQ-5c6b07da-3d06-414d-8770-4f438234b322）・素の文字列 src の拒否（REQ-99ca5381-6c53-426c-b145-7b4297c53868）を全てここで止める。この確認は`modules/common.nix` が共有する entriesType にも適用される（REQ-fc1c7ce6-dc9d-4dd3-98f5-7877d9f99d10）。root マーカーの subdir 適用形（REQ-08c8f639-790c-4970-a954-c9567538cf9b）の拒否（絶対パス・`..` 脱出・空の`subdir`、前置で target の `..` 脱出を隠さないこと）も同じ条件で止める。
* [root 解決を誤り、意図しないディレクトリツリーへ配置する](./20260809-24e0805d-53cd-40dd-9e7a-b5c4bbf2a298-root-resolution-wrong-tree.md) - 全ての配置先は `<root>/<target>` として組み立てられるため、root の解決を誤ると entry 単位の正しさに関わらず配置全体が別のツリーへ流れ込む。project mode の root を CWD 相対や config相対で採ってしまえば、リポジトリ外へ配置物を撒く。home mode の root を層ごとに定まった供給元以外から採れば、HM activation と CLI 直叩きで配置先が食い違う。
* [flock による直列化が破れ、同一 config への同時実行が互いの配置を壊す](./20260809-2b17fefb-6e92-4513-9e7c-de21897c9cfe-lock-serialization-broken.md) - 同一 `profileDir` に対する apply / rollback / reset は flock で直列化される（→ REQ-60c6b7ea-e936-4ce8-bd75-ad35e9c693b9 (2)(a)）。この直列化が破れると、2 つの run が同じ target 集合へ同時に書き込む。片方の古くなった配置の除去がもう片方の配置直後の symlink を消す、片方の undo journal がもう片方の書き込みを「自分が置いたもの」として巻き戻す、といった形で、どちらの run の巻き戻し保証も成立しなくなる。原子性の他のリスクが「1 run の中の失敗」を扱うのに対し、本リスクはその前提である「1 config を触るのは同時に 1 run だけ」の側が崩れる。
* [dryrun が副作用を残す、または本番 apply と異なる結果を報告する](./20260809-33e30498-6fa1-450b-a251-5624cbe837b9-dryrun-diverges-from-apply.md) - `apply --dryrun` はユーザーが「実行前に安全を確認する」ための唯一の手段であり、2 つの性質に依存している。読み取り専用であること（FS も flock も pending gcroot も触らない）と、報告するconflict / change が本番 apply の結果と一致することである。どちらが崩れても、dryrun は「安全確認」の役に立たなくなり、むしろ確認したつもりで壊す使い方になる。
* [--backup の rename 退避がユーザーの実データを上書き・喪失させる](./20260809-3719d298-8175-4501-95d5-75f3a29568fe-backup-aside-data-loss.md) - `apply --backup` は conflict の脱出ハッチとして、配置を塞ぐ記録外実体を`<target>.<suffix>` へ rename 退避する。退避対象は定義上「layat が記録していない実データ」であり、扱いを誤れば直接ユーザーのファイルを失わせる。
* [評価スイート自身の盲点でアサートが空虚に緑になる](./20260809-3de9753f-3fd3-4364-b1ab-64c68c15ec77-eval-suite-blind-spot.md) - 検証手段を nix-unit（点の不変条件）と namaka（面のスナップショット）の 2 本立てにする設計（DSG-fb49e36c-eb20-4efa-8cac-88ef0873db8e）には、その組み合わせに固有の盲点が 2 つある。どちらも「スイートが緑なのに守られていない」という形をとり、他のどのアサートの信頼性も同時に下げる。
* [レイアウト移行が部分適用で止まり、再実行しても収束しない](./20260809-3e8dd093-f21f-49c6-8d8c-7d62a6fad1e5-layout-migration-stuck-partial.md) - per-file 配置と dir symlink 配置の行き来、および symlink → copy の method 変更は、既存の配置物を配置前に除去してから新しい形を作る。この配置前除去は「除去してよいか」の判定と「途中で止まったらどうなるか」の 2 面で脅威を持つ。
* [--json のエンベロープが outturn 規約から外れ機械可読出力の消費側が処理に失敗する](./20260809-4936a47d-796b-4f1f-8ae4-eb87f6c64e71-json-envelope-contract.md) - `--json` の出力は layat をスクリプトから使う消費側にとっての契約であり、schema から外れた文書・実行ごとに形の変わる文書を出すと、消費側は自分のパーサが失敗して初めて気づく。破れても表に出にくいのが厄介で、layat 自身は正常終了したまま不正な文書を渡す。
* [manifest.json の形が engine の読む契約から気付かれずにずれる](./20260809-5df2d02b-e5d4-40eb-86ad-e8bc96e4c34d-manifest-contract-drift.md) - `manifest.json` は Nix 側と engine の唯一の安定契約（REQ-79ce0a09-f9bd-4e61-ba7f-45fb5643137b）で、`schemaVersion` は1 に固定され v1 のみを発行・受理する（REQ-250d936c-1df0-491d-a7af-708f38b61f33）。`normalizeManifest` が出す文書の形——トップレベルの必須 3 フィールドと任意の `identity`（REQ-dedd2c28-bba3-4ecf-80c9-8c77347e8e1f）・`rootKind` と fixed 時のみの絶対パス併記（REQ-dd10d820-e453-4099-a47a-ffb9a7de02fb）・entry の 5 フィールドと辞書順の配列化（REQ-0b0cd1e3-bfeb-45c1-978d-e2e11c568336）・marker の判別タグを漏らさないこと（REQ-1dcc9a33-b0f2-43e0-8310-fc4b19e68fe7）——が、評価層の変更で気づかれずに変わりうる。
* [世代スキップと lstat ドリフト修復が誤発火し、世代が無限に増えるかユーザーの編集を失わせる](./20260809-67e96e59-005f-439d-a230-834b0228801c-drift-repair-misfires.md) - project mode では、新しい link farm derivation が前世代と同一なら新世代を積まず、代わりに各 entry の target を `lstat` で確認して記録どおりでないものだけ再張りする（→ REQ-46fccb80-4bae-4d37-bc19-dded88e9a9c0）。この判定が誤ると、方向によって別々の被害が出る。
* [stdout の所有権と確認プロンプトの規律が崩れパイプ利用と非対話実行が正しく動かなくなる](./20260809-687993a2-4863-483c-a957-8a5d6faa4b82-stream-discipline-ux.md) - stdout は機械可読出力が専有し、人間向けのレポートと warning は stderr へ出す、という分離が崩れると、パイプへ流した出力に人間向けの行が混入して消費側のパーサが失敗する。とくに `--json`指定時は行指向の出力が全て止まらなければならず、コマンドを 1 つ足したときにその停止を配線し忘れるのが典型的な失敗の形である。逆に、stderr へ出すべき通知まで止めてしまうと、人間が実行したときに何が起きたのか分からなくなる。
* [途中失敗した run の巻き戻しが不完全で、FS に部分適用の痕跡が残る](./20260809-68e810c5-4e68-4b25-9bc0-6b2613022b49-undo-journal-rollback-incomplete.md) - apply / rollback が FS 変更バッチの途中で失敗したとき、その run が既に加えた変更が巻き戻されずに残る。逆操作そのものが誤っている（新規 symlink を消し忘れる・張替えのprevDest を復元しない・PreRemove が消した実ディレクトリを作り直さない・`--recopy` / `--backup` の rename 退避を戻さない）場合と、逆操作は正しいが適用順序が誤っている（LIFO でないため親ディレクトリを作り直す前に子 symlink を復元しようとする）場合のどちらでも起こる。
* [Nix と engine の唯一の契約である manifest の生成側と消費側がずれる](./20260809-7808768d-bd87-429a-af42-52e8559d940c-manifest-contract-skew.md) - `manifest.json` は Nix 側の評価と Go 側の engine をつなぐ唯一の安定契約であり、両側が同じ文書を同じ意味で読めることに全体が乗っている。ここがずれると、評価は成功しビルドも通るのに配置の段で意味を取り違える、という発見の遅い形で失敗する。
* [巻き戻し中の 1 件の失敗が残りの巻き戻しを道連れにし、復旧できない項目も報告されない](./20260809-a1622cdd-c7e2-4178-a50d-85bc2a35b29f-unwind-best-effort-lost.md) - undo ジャーナルの巻き戻しで個々の逆操作が失敗したとき、そこで巻き戻し全体が中断する。本来は best-effort で残りを巻き戻し切ってから、元のエラーと巻き戻せなかった項目の一覧をまとめて stderr へ報告して停止する契約である（→ REQ-9fca28c9-d3b1-4ad7-8f24-13b2ec7aeab2）。
* [profile のキーイングか世代の読み取りが誤り、別 config の世代系列を取り違える](./20260809-ac5cd9b4-58f9-43d8-9fae-66f7b5940beb-generation-lineage-corruption.md) - `profileDir` の解決規則か、そこに並ぶ世代リンクの読み取りが誤ると、layat は「前世代」に別 config の manifest を読む。前世代 manifest は古くなった配置の除去の入力そのものなので、取り違えればすぐに「別 config が置いた symlink を、この config の古くなった配置として消す」という誤削除に直結する。
* [reset の teardown が管理外の実体まで消し、preview と同意の条件も機能しない](./20260809-bb54245e-b284-4b4d-9896-8fec2b4e521c-reset-teardown-overreach.md) - `reset` は配置物を無い状態へ戻す FS-only teardown で、copy target を消す唯一の明示手段でもある（→ REQ-31f2882e-d2e3-4e3b-b783-feb627d73ac6）。削除だけを行うコマンドであるぶん、誤りの影響は片方向にしか出ない。消し過ぎは不可逆で、消し足りないぶんは次の apply が再配置するので実害が無い。
* [コピー中の syscall 失敗が握り潰され、中途半端な配置物と誤った成功報告が残る](./20260809-bc7526c2-2a2d-427f-9490-92d7d262fce3-copy-syscall-failure-swallowed.md) - copy は mkdir / open / read-write / readlink / lstat という複数の syscall の連なりで、どれもが権限・ENOTDIR・容量などで失敗しうる。個々の失敗を握り潰すと、部分的にしか書かれていないツリーが残ったまま apply が成功したように見え、ユーザーは破損した配置物を正常と誤認する。
* [失敗の帰属層と終了コードがずれ部分失敗の成否判定を誤らせる](./20260809-bd1e4ada-4a0d-4672-96cf-028f488c0540-error-layering-exit-code.md) - 失敗の表現には「誰がその失敗を持つか」という層の選択があり、層を誤ると消費側は失敗の原因を取り違える。entry スコープの失敗（配置先の衝突など）は当該 item が持つべきで、主体そのものが成立しなかった失敗（config の評価・ビルドの失敗）は subject が持つべきで、主体が確立する前の失敗はトップレベルが持つべきである。同じ失敗を 2 つの層に重複して載せると、消費側は失敗件数を二重に数える。
* [starter テンプレが展開直後に評価を通らず最初の体験で行き止まる](./20260809-c3e92bb8-5806-48b0-8910-ee4fe236a325-template-onboarding.md) - テンプレートは layat をはじめて使う人が最初に触れる成果物であり、展開した直後に評価が通らなければ、利用者は自分の書き方が悪いのか雛形に問題があるのか判断できないまま行き止まる。テンプレートはプロダクト本体のコードから独立して評価を通らなくなりうる（本体の API を変えたときに追従を忘れる）ため、本体のテストでは守れない。
* [フラグ解釈と nix 呼び出しの引数組み立てが仕様とずれ意図しない対象へ作用する](./20260809-c9197b73-483b-4d42-8541-49bee039f5ee-cli-surface-nix-argv.md) - CLI の表層は「どの対象に」「どの修飾で」作用するかを決める層であり、ここがずれると、正しいロジックが誤った対象に対して正しく動く。engine より下は無傷なので、テストが下層に偏っていると見逃される。
* [run が返す世代観測と到達状態が実態とずれ、機械可読出力の消費側を誤らせる](./20260809-cdcc6faf-9164-409b-b584-2921fa036d10-observation-payload-wrong.md) - `Apply` / `Rollback` / `Reset` は、実行結果として全 entry のインベントリ・世代観測（before / after）・失敗時の到達状態（どの target で落ちたか・どこへ到達しなかったか・巻き戻したか）・構造化された planner warning を返す。これが `--json` の envelope としてそのまま外へ出るため、値のずれは「FS の実態と機械可読出力の乖離」になる。
* [home-manager モジュールが engine をキックする配線から外れ native 機構へ翻訳される](./20260809-d734e24e-9af9-49f1-a22d-ade92f6554eb-hm-module-wiring.md) - 統合層のモジュールは engine を起動するだけの配線であり、entry を統合先の native な配置機構へ翻訳しない、というのが設計全体の前提である。この前提が崩れると、配置の意味論が統合層ごとに分岐し、engine が一手に引き受けているはずの不変条件（保守的な古くなった配置の除去・原子性）が使い方によって成り立たなくなる。
* [古くなった配置を保守的に除去するときの不変条件が破れ、layat が作っていない実体を消す](./20260809-e3d42a21-1f43-4ac6-835e-a5caf8d86363-stale-removal-invariant-broken.md) - 古くなった配置の除去は「前世代 manifest に記録されており、かつ実 FS 上のリンクが記録先を指したままである」symlink だけを対象とする。この不変条件は plan 時に一度判定されるが、plan から unlink までの間に実 FS が変化しうるため、除去の直前に再検証する必要がある。再検証を欠くか、条件のどれかを緩めれば、ユーザーや他ツールが置いた実体を消す。
* [空親ディレクトリの剪定が行き過ぎ、または残骸を残す](./20260809-e659f9dd-fbc9-48aa-8ae5-ecc4faf2a85c-ancestor-pruning-overreach.md) - target を除去した後、空になった親ディレクトリのチェーンを root 境界まで剪定する。親をたどるこの処理は両方向に失敗しうる。止まるべきところで止まらなければ、ユーザーのディレクトリ（root 自体・symlink である祖先・layat 管理外の空 dir）まで消す。逆に剪定を怠れば、apply のたびに空ディレクトリの残骸が積もる。
* [配置分類を誤り、利用者の実体を本人に知らせずに破損させる](./20260809-e8449214-7794-4d0d-b584-a3a152e2c1f9-placement-classification-misjudged.md) - engine は target の現況を「不在 / 自プロファイルが前世代で記録した symlink / 記録に無いforeign symlink / 通常ファイル・実ディレクトリ」に分類し、それぞれ新規配置・無警告の張替え・警告付き後勝ち・conflict 停止へ振り分ける。この分類を誤ると、ユーザーが自分で置いたファイルを警告なく上書きする（回復不能）、あるいは自分が前世代で張ったリンクにまで foreign 警告を出して毎回のノイズにする、という両方向の失敗が起きる。
* [entrypoint の形ごとに root 解決と配置の意味論が食い違う](./20260809-e916f742-59a3-4202-a316-603a908fd0db-entrypoint-root-resolution.md) - layat は flake の entrypoint と legacy の非 flake entrypoint という 2 つの起点を持ち、project mode ではさらに git から root を解決する。起点が増えるほど「同じ配置のはずなのに起点によって結果が違う」という食い違いが入り込む。
* [GC アンカーの対象と名前を取り違えて世代が回収不能になる](./20260809-f67a0883-950a-4458-8b6d-1f95cb039cb1-farm-anchor-mismatch.md) - symlink farm は GC アンカー専用で、アンカーは store-backed な symlink entry に限る（REQ-b12fc3c0-d7fe-4003-922c-f3ac0d969b66）。アンカー名は target のハッシュ（REQ-62eda895-efd4-4eaf-a58b-600e8637da75）で、farm derivation は`mkManifest` の返り値に含まれる（REQ-60e6b49c-9ba1-4552-a0ec-d340421ec281）。
