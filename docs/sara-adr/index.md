# SDR（`sara_adr`）

* [ADR は単独で覆せる 1 つの決定だけを書く](./20261101-1afa3a31-224d-492d-96d9-d3f6c9cb20cd-adr-one-decision-granularity.md) - layat の ADR は、1 本に複数の決定を束ねて書いてきた。後から 1 つの決定だけを変えると、元の ADR に改訂注記を足して「この節だけが変わった」と示すしかない。改訂を 4 回以上受けた ADR は 13 本あり、どの決定がいまも有効かは注記を順に読んで組み立て直さないと分からなくなっていた。 (stable)
* [model.yaml で組み込みモデルを全面置換し、汎用の型名を使う](./20261101-2457aa00-fab7-4c99-af53-2e6643c21c79-model-yaml-full-replacement.md) - sara は組み込みのモデル（型と relation）を持ち、カスタムスキーマで置き換えられる。置き換えは全面で、部分的なマージはできない。組み込みには `hardware_requirement` や `system_architecture` のように、layat に対応する実体の無い型が含まれる。 (stable)
* [ADR の失効は supersedes と 廃止 で表す](./20261101-3ff9f355-a667-476e-b10d-087248cdbfcf-adr-supersedes-and-deprecated-status.md) - `docs/model.yaml` は、ADR 間の関係として節単位の部分改訂を表す `revises` だけを持っていた。文書丸ごとの失効を表す `supersedes` と、ステータスの `廃止` は持たなかった。当時は丸ごと失効したADR の実例が無く、実例の無い関係を先に置くと部分改訂に誤用されると考えたためである。 (stable)
* [ADR の規則を汎用とプロジェクト当てはめに分けて書く](./20261101-441fb006-a2f4-44f2-bc69-bb0eeee81893-adr-rules-generic-and-project-split.md) - ADR の規則は `docs/adr/README.md` に、layat の ADR 番号・型の区分・実データと同じ文書に書かれていた。 (stable)
* [省略形の禁止は起票の機械化と全面移行で担保する](./20261101-4656dd7b-0ea4-48fb-a6c4-a8c96ad50103-short-form-ban-enforced-by-tooling.md) - 8 文字の省略形を使わないという規則は SDR-722ce265-2aaf-4a90-915d-32d26b7a38bb が決めた。本 ADR は、その禁止をどう担保するかだけを決める。担保の方法は、禁止の規則を変えずに単独で覆せる。後から CI の検出を入れるなら、本 ADR だけを廃止すればよい。そのため規則とは別の ADR にする。 (stable)
* [概要文書は item へのリンク集に縮退させる](./20261101-536848bb-8901-4e73-8c66-861de3f91bcd-overview-docs-as-link-index.md) - ドキュメントを item に分割する決定（SDR-5ea31001-96f8-4324-a40b-647cdfa5cc9d）で、`docs/spec.md`・`docs/design.md`・`docs/concept.md` の規範的な内容は item へ移る。元の 3 文書をどう扱うかを決める必要があった。 (stable)
* [ドキュメントは sara のナレッジグラフとして item に分割する](./20261101-5ea31001-96f8-4324-a40b-647cdfa5cc9d-docs-as-sara-knowledge-graph.md) - layat の仕様・設計・テストは、`docs/spec.md`・`docs/design.md`・`docs/concept.md` と ADR に散文で書かれていた。この形では、要求とリスクの紐付けが一貫しているかを機械的に確かめられない。 (stable)
* [ID はフル UUID に統一し 8 文字省略形を使わない](./20261101-722ce265-2aaf-4a90-915d-32d26b7a38bb-full-uuid-ids-no-short-form.md) - item の正式 ID はフル UUIDv4 だが、ファイル名と散文中の参照には前方 8 文字の省略形を使っていた。フル UUID は人が読めないという前提への対処だった。 (deprecated)
* [item にできない外部参照は text フィールドへ逃がす](./20261101-9f2ef734-a9a7-4b93-92a7-e8ed1c7cf8fe-external-references-as-text-fields.md) - ADR は GitHub の Issue や、決定の起点になったセッションを参照する。これらは sara の item ではないので、relation では表せない。relation の参照先は実在する item でなければならず、実在しない ID は破損した参照として検出される。 (stable)
* [sara 品質管理機構の決定は sara_adr 型に分ける](./20261101-c15921a9-7aea-407c-a34b-7465783b1af1-sara-adr-type-for-doc-process-decisions.md) - `docs/adr/` には、layat 本体の設計判断と、sara による品質管理機構（`docs/model.yaml`・グラフの検証・起票ラッパー・item の運用規約）の設計判断が混在していた。後者は layat に固有ではなく、#500 で別のリポジトリへ切り出す予定がある。 (stable)
* [提案を棄却した決定は status 不採用 で記録する](./20261101-d5304533-00ae-423b-a459-7c67c1cf093c-adr-status-rejected.md) - ADR の `status` は、実データの表記に合わせて日本語の値を持つ enum にしている。組み込みの英語の値（`proposed` / `accepted` / `deprecated`）は使っていない。 (deprecated)
* [ADR も UUID で採番し、連番の旧 ADR は legacy_adr 型に凍結する](./20261101-e093c6b2-75fd-4c91-a8f0-5a89e005e4ed-adr-uuid-ids-and-legacy-type.md) - ADR だけは連番（`ADR-NNNN`）で採番してきた。既存 ADR の相互参照やコミットメッセージでの言及を無効にしないためである。一方、並列レーンで ADR を起こすと、複数のレーンが同じ「次の番号」を取る構造が残っていた。 (deprecated)
* [sara-id を廃止し sara init を包む起票ラッパーを使う](./20261101-f5443db0-6407-41c0-9ab5-55f22dc4de5e-sara-new-wrapper-replaces-sara-id.md) - `sara-id` は devShell 同梱の採番コマンドで、UUIDv4 の採番・8 文字の重複の確認・省略形の出力・型名からprefix への写像・ファイル名素材の組み立てを担っていた。item ファイルの作成は `sara init` が担当した。 (stable)
* [adr の status_note を持たない](./20261101-fa7eff8e-788f-48e7-951d-4cfbf95d5a1f-adr-status-note-removed.md) - ADR のステータス行には「採用（2026-06-14 改訂: … → ADR-0015）」のようなカッコ書きの改訂注記が付いていた。enum の値に収まらないので、frontmatter に `status_note` フィールドを設けて受け皿にしていた。 (stable)
* [risk の impact を検出後の回復可能性で採点する](./20261103-0fd284d6-60dc-4c04-a413-3d7926ae10ac-risk-impact-as-recoverability.md) - risk の `impact` の high 行は、「ユーザー環境・実データの破壊」と「沈黙の不整合を残すこと」を並べていた。気づかれないまま通る脅威は、開発の中に留まるものでも high を採る読み方だった。 (stable)
* [複数の失敗方向を持つ risk は最も重い方向で採点する](./20261103-1a02013e-c57b-4079-9c72-8e9fe99e499a-risk-heaviest-direction.md) - risk の `impact` は検出後の回復可能性で採点する（SDR-0fd284d6-60dc-4c04-a413-3d7926ae10ac）。1 つのrisk が複数の失敗の仕方を持ち、方向によって回復できる度合いが違うとき、どの方向で採点するかを決める必要があった。 (stable)
* [ADR の justifies 対象を specification を持つ全型に広げる](./20261103-1d295034-9bab-4e30-9ead-173e5f56c396-adr-justifies-quality-and-test-plan.md) - ADR 系の型の `justifies` は、`requirement` / `design` / `infrastructure` だけを対象にしていた。quality とtest_plan を設けた（SDR-34916a83-0cff-4524-a8ff-5a3195af52c3）ことで、規範の文を持つ型が増えた。 (stable)
* [infrastructure を技術基盤として再定義し root から外す](./20261103-29ef8bb4-9349-47db-9e79-926bc71bbdd0-infrastructure-redefined-non-root.md) - infrastructure は root の型として定義されていた。satisfy できる相手が design しか無く、CI やトレーサビリティ検証のような開発の基盤は design の木に属さないため、root にせざるを得なかった。その結果、`docs/infrastructure/` の item は全件が構造上の接続漏れだった。 (stable)
* [テスト計画の型を品質方針の型から分けて設ける](./20261103-34916a83-0cff-4524-a8ff-5a3195af52c3-quality-and-test-plan-types.md) - テスト計画や品質方針にあたる文書は、受け皿の型が無いため `requirement` として置かれていた。`requirement` の親は use_case だが、これらの文書は「ユーザーがどう使うか」から導かれないので親を持てず、接続漏れのまま残っていた。 (stable)
* [design の satisfies 対象に test_plan を含める](./20261103-35636015-710a-4cf8-b6ba-48ca047efed0-design-satisfies-test-plan.md) - design の `satisfies` は `requirement` だけを対象にしていた。テスト計画にあたる `requirement` を test_plan へ移す（SDR-34916a83-0cff-4524-a8ff-5a3195af52c3）と、それらを `satisfies` で指していた design item の辺は張り先を失う。中には `satisfies` がその 1 本だけの design item もあり、移した途端に design 側が接続漏れになる。 (stable)
* [ADR は UUID だけで採番する](./20261103-3e5b9994-a905-44d8-8256-2bd65b12b87e-adr-uuid-only-numbering.md) - 連番で採番していた旧 ADR は、UUID で採番する新 ADR と並べて `legacy_adr` 型に凍結していた。旧 ADR の決定は 1 決定 1 ADR の新 ADR へすべて移り、旧 ADR は全部 `廃止` になった。docs/adr の外の参照も新 ADR の ID へ付け替え終えている。 (stable)
