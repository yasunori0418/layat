# 欠陥を既存の RISK / TC に辿れたかで分類して数える

- ステータス: stable
- 日付: 2026-11-14
- 関連: [欠陥 issue のクローズ時にテスト系 item の欠落を追補する](defect-close-backfills-risks.md), GitHub Issue #651, `docs/agents/triage-labels.md`
- 起点: epic #651 の grilling（2026-11-14）で確定

## 背景

[欠陥 issue のクローズ時にテスト系 item の欠落を追補する](defect-close-backfills-risks.md) により、
欠陥の Issue をクローズする前に、その欠陥を捕まえられたはずの risk / test_condition が欠けていな
かったかを問い、欠けていれば追補する。ただし、問うた結果は Issue ごとの記述に書かれるだけなので、
リスク分析が欠陥をどれだけ予見できていたかを後から数えられない。

## 決定

欠陥の Issue をクローズするときに、その欠陥に対応する risk か test_condition が、Issue を起票した
時点で既にあったかどうかで欠陥を 2 つに分類する。分類は固定した語彙で記録し、後から数えられる
ようにする。欠陥ではないと判断して閉じた Issue は分類しない。語彙の綴りはこの決定には書かず、
トラッカーのラベルを定める運用文書が持つ。

## 根拠

起票した時点で対応する risk か test_condition があったかを数えると、リスク分析が欠陥を予見できて
いた割合が分かる。予見できていなかった欠陥が多ければ、分析の進め方を見直すきっかけになる。

分類の時点をクローズ時にするのは、トレースと feed back を書き終え、対応する item の有無が確定して
いるため。判定の基準を起票の時点の状態に固定するのは、クローズ前の状態で判定すると、feed back で
item を追補した欠陥が「既にあった」と判定されてしまうため。

## 棄却した代替案

### 本文の定型行で数える

Issue の本文に分類の行を書き、検索で数える。本文の書式は Issue ごとに崩れやすく、`gh` で件数を
数えるには本文を取得して解析する必要がある。固定した語彙で記録すれば、絞り込みの条件だけで件数を
数えられる。

### 発見と予見の両方をラベルで数える

テストケースの実行で露見したか（発見）と、対応する risk か test_condition が既にあったか（予見）の
2 つの軸をラベルにする。発見の軸は、本文のトレースに露見させたテストケースを書くかどうかで既に
分かる。ラベルを 2 軸に増やすと付け忘れと付け間違いが増える。

### クローズ前の時点の状態で判定する

クローズ直前に対応する risk か test_condition があるかで判定する。feed back で item を追補した
欠陥も「既にあった」と判定され、予見できていた欠陥と区別できない。

### 分類を記録せず数えない

追補の要否を問うだけにとどめる。予見できていた割合が分からず、リスク分析を見直すきっかけが
得られない。
