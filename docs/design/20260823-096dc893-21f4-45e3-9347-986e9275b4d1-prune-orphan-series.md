# DSG-096dc893-21f4-45e3-9347-986e9275b4d1: prune を paths の列挙・engine の判定と削除・CLI の同意解釈に分け、engine API を Reset と同型にする

## 設計

`nput prune` を 3 層に分ける。既存コマンドと同じ層境界（→ DSG-7d354fe0-a333-495b-9f4b-14bba316dc47）に
乗せ、prune 専用の縦割りを作らない。

```
internal/paths/    ← roothash 系列の列挙と backref の読み取り。ListRootHashSeries / ReadBackref
internal/engine/   ← root 実在の判定・try-lock・os.RemoveAll。Prune / PruneOptions / PruneResult
cmd/nput/          ← TTY 判定・--yes・--json の解釈と、確認プロンプトの提示
```

**`internal/paths`** はプロファイルレイアウトの計算を既に持つ層で（`Resolve` / `Base` /
`RootHash`）、`<roothash>` 階層の形と backref `.root` の位置を知っているのはここだけ。列挙
（`ListRootHashSeries`）と backref 読み取り（`ReadBackref`）をここへ置くと、レイアウトの知識が
1 箇所に留まる。この 2 関数は prune 専用ではなく、`nput status`（→ #198）が同じ列挙を使う。

この配置は `internal/paths` の性格を変える。TP-e7c25263-6d2d-4a37-8275-26906889d912 は同
パッケージを「FS に一切触れずに判断する層」（state ディレクトリ・世代パスの解決・root の
ハッシュ化）として名指しし、入力が列挙可能だから table-driven のユニットで覆えと規範化して
いるが、`ListRootHashSeries` はディレクトリを走査し `ReadBackref` はファイルを読む。**この
2 関数は同 TP の言う純ロジック層の例外**であり、入力が FS の状態である以上 table では覆えない。
既存の純関数（`Resolve` / `Base` / `RootHash` / `GenerationLink`）はこれまでどおりユニットの
table で覆い、新設 2 関数は tmpdir を張った実 FS の統合レベルで覆う（同 TP が engine に対して
定める主戦力と同じ層）。`internal/planner` の FS プローブが「判定材料の読み取りは純ロジック層
に含む」として扱われているのと同じ切り分けで、判定そのものは engine 側にある。

**`internal/engine`** が root の実在判定・lock・削除を持つ。FS 意味論の実行は engine の担当で
（→ DSG-8b96869c-842e-4f78-8ff7-df1f1d6c1a68）、prune もその例外にしない。

**`cmd/nput`** は TTY 判定と `--yes` / `--json` の解釈だけを持つ。engine が見るのは `Confirm`
コールバックの戻り値までで、同意をどう取ったかは知らない（`reset` と同じ分担）。

### engine API は Reset と同型

```go
type PruneOptions struct {
    StateDir string
    DryRun   bool
    Confirm  func(*PruneResult) (bool, error)
    Warnf    func(format string, args ...any)
}

func Prune(opts PruneOptions) (*PruneResult, error)
```

`ResetOptions` の `DryRun` / `Confirm` / `Warnf` をそのままの意味で持つ（→ `internal/engine/reset.go`）。
違うのは、prune が config を名指ししないため `Name` / `RootKind` / `WorkDir` / `Git` を持たず、
入力が `StateDir` だけになる点。entrypoint 発見も nix eval / build も行わない。

`DryRun` は列挙と判定だけを行い、lock も取らず FS を変えない。`Confirm` は非 nil のときだけ
呼ばれ、削除直前に判定済みの `PruneResult` を渡す（root パス一覧がここに入っているので、CLI は
それを表示する）。false を返したら削除せず `Aborted` を立てて返る。

```go
type PruneResult struct {
    Removed []PruneSeries  // 削除した（dryrun では削除予定の）系列
    Skipped []PruneSkipped // 対象外にした系列と理由
    DryRun  bool
    Aborted bool
}

type PruneSkipped struct {
    Series PruneSeries
    Reason PruneSkipReason
    Detail string
}
```

`PruneSkipReason` は `"locked"` / `"backref-unreadable"` / `"root-stat-failed"` の 3 値。判定材料が
欠けた系列を黙って落とさず、理由付きで返す（→ REQ-c44433a1-7ee7-459a-9aae-7cc42166876f の
「安全側へ倒す」）。root が実在していて対象外になった系列は失敗ではないので `Skipped` に入れない。

**`Skipped` に入る全ケースで `Warnf` を呼ぶ。** 3 値のいずれであっても、系列を残した理由は
warning として出す。`Skipped` に構造化して返すのは CLI がまとめて扱うためで、`locked` だけ
warning・判定不能系は黙殺、という不揃いは REQ-c44433a1-7ee7-459a-9aae-7cc42166876f の
「その理由を warning として報告しなければならない」に反する。

**削除中の失敗は `Skipped` ではなくエラーで返す。** `os.RemoveAll` が途中で失敗した系列は
「消さないことにした」のではなく「消し始めて完了しなかった」ので、判定段の 3 値とは別物として
扱う。部分削除された系列を `Removed` に数えず、その系列を特定できる形でエラーを返し、後続の
系列へは進まない（`Removed` には失敗より前に完了した系列だけが入る）。`.root` が先に消えると
以後その系列は走査対象から外れて手動削除もできなくなるため、削除順は `.root` を最後に回す。

**フィールド名に `Pruned` を使わない。** `Result.Pruned` が既に「除去後に rmdir した空祖先
ディレクトリ」の意味で埋まっており（→ REQ-8409db86-a1ba-4053-86dc-588985cc1ca7）、prune の
削除系列を同じ語で呼ぶと同じ構造体群の中で 2 つの意味が衝突する。削除した系列は `Removed`。

### root の判定条件は 1 つだけ

判定は 2 段。**前段が backref の妥当性検査**で、`ReadBackref` が返した値が読めない・空・絶対
パスでないのいずれかなら、root パスが決まらないので `backref-unreadable` で skip する
（`filepath.IsAbs` で弾く。ここで弾かないと相対パスが `os.Stat` の cwd 相対解決に流れ、無関係な
パスの実在で判定が決まる）。

前段を通った root について、**後段は `os.Stat(root)` の 1 条件**。`fs.ErrNotExist` のときにだけ
孤児と判定し、`nil` は生存、それ以外のエラーは判定不能として `root-stat-failed` で skip する。
条件を 1 つに保つことで、判定材料が欠けたときに削除へ倒れる経路が構造的に生じない。`os.Stat` は
symlink を辿るので、dangling symlink の root は追加の分岐なしに不在として落ちる。root だった
パスがファイルに置き換わっていれば `nil` が返って生存側に落ちるが、これは意図した帰結（条件は
「実在しない」だけで、種別は見ない）。

### lock 規律

系列の削除前に、その系列内の**全 `<name>` profileDir** を try-lock で取る（lock の鍵は
profileDir 単位 → `internal/lock`）。

- 1 つでも `ErrLocked` なら**系列ごと skip**（`locked`）。既に取れていた分は即 `Release` する
- `ErrLocked` 以外の `Acquire` エラーも同じく skip + warning（判定不能を削除へ倒さない）
- 全部取れたら**保持したまま** `os.RemoveAll(<roothash>)` し、その後 `Release` する
- `<name>` を 1 つも持たない `.root` だけの系列は、lock の鍵になる profileDir が無いので lock
  なしで削除する

系列単位で all-or-nothing にするのは、`<roothash>` ごと消す削除単位に lock の粒度を合わせる
ため。一部の `<name>` だけ lock を取って部分削除すると、生きている `<name>` を持つ系列が
半端に壊れる。

### 世代を持たない系列も対象

`.pending` と `.root` だけがあり世代リンクが 1 つも無い系列も、root 不在なら削除する。実機の
孤児 95 件のうち 54 件がこの形で（開発者環境での実測・2026-08-23 の Issue #127 分割時点）、
「世代がある系列」に限ると過半が残る。列挙は `.root` の有無で行い、世代の有無を条件にしない。

### この設計が引き受ける代償

判定ロジックが新規で、既存の配置系ゲート（planner の分類・stale 除去の保守的不変条件）の
どれにも乗らない（→ RISK-f522a51b-db4b-4164-bd20-63fa4a0cb27d）。安全機構の側は `reset` の
確認・dryrun 経路と同型にすることで既存のテストと規律に乗せているが、乗り切らない分は
残る（→ RISK-0909e121-8ec4-40c8-ab1c-562e61f31067）。
