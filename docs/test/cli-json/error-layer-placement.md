# 失敗が item と subject とトップレベルの正しい層に 1 度だけ載り原因で分類される

## 条件

失敗の帰属層が原因の性質で決まり、かつ 1 つの失敗が 1 つの層にしか載らないことを確かめる。

- **entry スコープの失敗は item が持つ** — 配置先の衝突のように、特定の対象に閉じた失敗は
  当該 item が失敗として持ち、subject の errors へ重複させない。重複すると消費側が同じ失敗を
  二重に数える
- **主体が成立しなかった失敗は subject が持つ** — 評価やビルドの失敗のように、その config に
  ついて結果が存在しない失敗は subject の errors に 1 件だけ載る。このとき item は空になる
- **主体が確立する前の失敗はトップレベルが持つ** — subject を特定できない段階での失敗は
  トップレベルの errors に載る。逆に subject を列挙し終えた後はトップレベルに載せない

原因の分類も条件に含む。ビルド失敗のマーカーが途中で再ラップされても残ること、ファイル
システム由来の失敗と排他制御由来の失敗がそれぞれの分類を得ること、いずれにも当たらない失敗が
汎用の分類になること。分類が区別されなくなると、消費側は原因で分岐できない。

`--all` の部分失敗では層の分離が最も崩れやすいため、1 つの config の失敗が兄弟 config の
ステータスやインベントリを変えないことを確かめる。読み取り系の `--all` は途中で失敗しても
そこまでの subject を残し、失敗した config に error を載せ、以降を subject 化しない。
