# engine の実行結果から JSON ペイロードへの写像が実際に起きたことと食い違う

## リスク

schema に適合していても、その文書が述べている内容が実行の事実と食い違えば、消費側は
「正しい形式で嘘をつかれる」ことになる。適合チェッカはエンベロープの形しか見ないため、
この層は写像そのものを検証しない限り守れない。

食い違いは次の軸で起きる。

- **インベントリの取りこぼし** — item は新 manifest の entry と前世代から古くなった配置として除去された
  entry の全数であるべきところ、片方だけになる
- **change の過不足** — 差分のある遷移だけが change であるべきところ、no-op な再 link まで
  change として立つ（実際には何も起きていないのに変更を報告する）、あるいは method 変更
  （symlink → copy）が 1 item + 1 change へ束ねられず二重計上される
- **世代番号スロットの誤り** — 変更前後の世代を持つべき実行で欠ける、逆に世代の概念を持たない
  実行（reset）や profile 未作成の dryrun でスロットが 0 や null として現れる。nil を省略
  するつもりのフィールドがゼロ値へ化けるのは schema 上は合法なので、適合検証では捕まらない
- **inventory を持たない読み取り系の情報欠落** — 列挙結果が `info` に載らない、あるいは
  0 件のときにキーごと消えて「列挙していない」と区別できなくなる

[prune --json はトップレベル info の removed に削除系列を、skipped に判定か削除に至れず残した系列を載せる](../requirements/prune-json-payload.md) が定める `removed` と `skipped` が実際に削除した系列や残した系列と食い違うのも、
この写像の誤りである。エンベロープを組み立てる実装を置き換えても消費側はこの一覧を読むので、
懸念は `requirement` の側に残る。

## 影響

消費側が実行結果を誤って解釈する。何も変わっていないのに変更を検出したと判断する、あるいは
変更に気付かない。impact を medium とするのは、FS の配置そのものは破損せず、写像を直したうえでの
再実行が正しい文書を返すため。ずれが検出されないまま消費側へ渡る点は脅威の性質として重いが、
気づいた後の回復可能性は下げない。nil を省略するつもりのフィールドがゼロ値へ化けるのは
schema 上は合法で適合検証では捕まらず、消費側は「正しい形式で嘘をつかれた」ことに気づく契機を持たない。
likelihood を medium とするのは、写像の分岐（no-op 抑制・coalesce・世代スロットの有無）が実行の
組み合わせごとに増えるためで、実装の素朴さに依存する種類の誤りではない。
