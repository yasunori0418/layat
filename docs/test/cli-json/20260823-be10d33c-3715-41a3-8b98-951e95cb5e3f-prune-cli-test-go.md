# CASE-be10d33c-3715-41a3-8b98-951e95cb5e3f: prune_test.go — prune の確認ポリシー・root パス一覧の提示・ストリーム排他と --json の形状

## 対象

`cmd/nput/prune_test.go`

`nput prune` の CLI 面（TTY 判定・`--yes` / `--json` の解釈・確認プロンプトの提示・
`--dryrun` の出力・`--json` の payload）を検証する。engine を実 FS で駆動するのは
CASE-49ac6d68-ed29-41aa-b939-dcfdc8711082 の担当で、こちらは engine の結果値を組み立てた
fixture を CLI の関数へ通す。engine 本体は呼ばず、CLI が持つ 2 つの seam（engine の
呼び出し口と対話性判定）を差し替えて駆動するので、実 state dir にも実 TTY にも依存しない
（`go test` の標準入力は決して TTY にならないため、対話経路は seam 無しでは到達できない）。

TC-a9857bf7-f7f9-41f9-b42c-9993fd16a5e9 が「CLI が root パス一覧を実際に表示するかは
cli-json 区分の残余」として残した部分を、ここが引き取る。

## 検証内容

- **確認ポリシー** — プロンプトを出せるのは TTY のときだけで、`--json` は TTY でも常に
  禁じる側へ倒れること。共有の確認ポリシーと合成すると、`--json` + 同意フラグ無しが
  プロンプトを出さずに即拒否になり、同意フラグを足せばプロンプト無しで進むこと
  （→ REQ-42fe312c-927c-4da3-9346-f7ca2f3a58ed の `--json` fail fast）
- **拒否の名指し** — 確認ポリシーは reset と共有するが、拒否のメッセージが prune を名指し
  すること（共有した結果として別コマンドの名前が出ると、読者が直すべきフラグを取り違える）
- **root パス一覧の提示** — 確認の直前に出す一覧に、削除対象の**全系列の root パス**が
  含まれること。アンマウント中の root を消えたものと取り違えないための唯一の防壁なので、
  1 系列だけでは満たせない fixture（state 基底と system 基底の 2 系列）で見る
  （→ ADR-0034 §2）。期待する root は fixture からループで引かずリテラルで書き、件数の
  ヘッダと実際の行数の一致も見る（結果値を読み直して期待にすると、自分と辻褄が合うだけの
  一覧が通る）
- **確認へ渡る値** — 確認コールバックが表示するのが engine から渡された **preview** である
  こと。preview は戻り値とは別の値で、戻り値の側の削除系列は abort 時に空になるため、戻り値を
  表示する実装だと「0 件」と読める一覧を見せたまま削除へ進む
- **実行の筋道** — 同意フラグが無ければ確認コールバックを渡し、あれば渡さないこと。拒否
  された実行は stderr へ中止を告げて成功終了し（終了コードは 0）、`--json` のインベントリの
  削除系列が空配列になること
- **ストリームの排他** — `--dryrun` の系列一覧は stdout をタブ区切りで専有し、確認の提示と
  事後の結果レポートは stderr へ出して stdout を汚さないこと。`--json` のときは行指向の
  stdout が止まること。削除対象 0 件のときは stdout が空のまま stderr の通知が両契約で残り、
  結果レポートは no-op を告げること
  （→ REQ-fea038de-55eb-45ac-87fc-ec3a7287592a、REQ-2353259f-5878-452a-8e11-3445de69abc2）
- **`--json` の形状** — 削除（予定）系列が `removed`、残した系列が `skipped` に載り、
  `pruned` というキーが現れないこと（`pruned` は空祖先ディレクトリの剪定で既に埋まっている
  → REQ-8409db86-a1ba-4053-86dc-588985cc1ca7）。skip 理由は engine の語彙 5 値がそのまま
  出て、CLI 側で綴り直されないこと。系列 0 件でも `removed` / `skipped` が配列で残ること。
  prune は config を名指ししないので `results` は空で、インベントリはエンベロープ全体の
  `info` に乗ること。文書は niface の適合チェッカを通ること
- **走査前の失敗で info が出ない** — `--json` + 同意フラグ無しの拒否は走査の前に起きるので、
  エンベロープに `info` が現れないこと（空のインベントリが出ると「走査したが 0 件だった」と
  読める）
- **`--dryrun` の非破壊性** — CLI が組み立てる engine オプションが、dryrun 側では
  `DryRun` を立てて確認コールバックを渡さず、非 dryrun 側ではその逆になること。走査基底は
  どちらの経路でも空のまま engine へ委ねること（CLI が基底を名指ししない層分けの担保）

engine の結果値を直接組み立てるので、実 FS も nix も要らない。
