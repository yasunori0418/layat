# CASE-b19188cb-e3f0-4c52-8c92-6db96bbbb45a: e2e 08-prune — 実 apply が作った系列を root 削除で孤児にし、prune が系列ごと消して gcroot が外れる

## 対象

`tests/e2e/scenarios/08-prune.sh`

`e2e_isolate` で仮 `$HOME` と `$XDG_STATE_HOME` を切り、projectRoot の fixture flake を持つ
git repo を 2 つ用意して実 nix 経由で apply する E2E シナリオ。root（git toplevel）ごとに独立した
`<roothash>` 系列が立つので、一方の root を `rm -rf` して孤児にし、もう一方は生存させたまま
`nput prune` を駆動する。

判定分岐そのものは `CASE-49ac6d68-ed29-41aa-b939-dcfdc8711082`（tmpdir に手で組んだ fixture）が
覆っている。**このシナリオの持ち分は「実 apply が置いた本物のレイアウトを prune が拾えるか」**で、
手組み fixture では `.pending` / 世代リンク / `.root` の形と `nix-env --set` が張る indirect
gcroot を再現しないため、engine のユニットだけでは実機で系列が残る退行を拾えない。

走査基底は 2 つあるが（→ ADR-0036 §3）、system 基底 `/nix/var/nix/profiles/nput` は実機の共有
状態なので**このシナリオは触らない**。検証は `$XDG_STATE_HOME` 側の系列だけで行う。

## 検証内容

- **apply が作るレイアウト** — project mode の apply が `<roothash>/.root`・`<roothash>/docs/profile`
  （symlink）・`<roothash>/docs/profile-1-link` を置く。系列ディレクトリは roothash の計算式を
  シナリオへ写さず、置かれた `.root` の内容から引く（実装との二重管理を避ける）
- **prune 前の gcroot** — `nix-store --gc --print-roots` に孤児予定系列配下のリンクが現れる。
  `<state>` 配下の out-link と世代リンクは `/nix/var/nix/gcroots/auto` 経由の indirect root で、
  系列を消すまで store path を保持し続ける（GC 回収の陽性対照）
- **`prune --dryrun` の非破壊性** — 孤児系列を `remove-series` 行に root パス付きで挙げ、生存
  系列は挙げない。実行後も `.root` と世代リンクが残る（→ ADR-0034 §2）
- **`prune --dryrun --json`** — 同じ在庫をエンベロープの `info.removed` が運ぶ。prune は config を
  名指ししないので `results` は空配列のまま。孤児系列の `root` と `names`（`["docs"]`）が載り、
  生存系列は載らない（→ issue #134）
- **`prune --yes` の削除** — 孤児系列は `<roothash>` ごと消え、生存系列の `.root` と profile
  symlink は残る
- **配置物の不変** — 生存 root 配下の配置 symlink と内容は prune の前後で変わらない
- **GC 回収可能になったこと** — `print-roots` から孤児系列配下の gcroot が消え、生存系列の
  gcroot は保持される。実 GC は回さず、root として数えられなくなったことで見る
- **再実行の no-op** — 孤児が無い状態での再実行が生存系列を消さない
