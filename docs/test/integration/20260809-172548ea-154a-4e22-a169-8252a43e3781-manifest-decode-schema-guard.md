# TC-172548ea-154a-4e22-a169-8252a43e3781: manifest の読み取りが v1 を正確に復元し版の境界・未知フィールド・不整合な root 種別を拒否する

## 条件

契約の消費側が、渡された文書をどう読みどう拒むかを確かめる。

- **v1 の正確な復元** — 配置元の種別・配置元・部分パス・配置先・配置方式・root の種別が
  定義どおりに読み取れること
- **未知の版の拒否** — 消費側が知らない版を受理せず、しかも**その理由が判別できる形で**
  拒否すること。呼び出し側が「pin した flake と CLI の版がずれている」という案内を出せる
  ことが契約であり、単にエラーになるだけでは足りない
- **版の下限をまたぐ受理と拒否** — 消費側が定める最小の版に満たない文書を受理せず、下限
  そのものは受理すること。下限割れは版ずれではなく壊れた文書なので、未知の版と同じ判別可能な
  値では包まない。包んでしまうと呼び出し側が的外れな「flake と CLI の版がずれている」案内を出す
- **未知のフィールドの拒否** — 知らないキーを黙って無視せず拒否すること。無視すると契約が
  暗黙に拡張され、届かなかった情報に誰も気づかない
- **root の種別ごとの扱い** — 評価時に絶対パスが決まる種別がパスを持つこと。対になる「実行時に
  解決する種別がパスを持たないこと」も条件に含め、パスを併記した文書を拒否すること。併記された
  パスは後段の root 解決が参照しないため、受理してしまうと利用者が書いた配置先が黙って無視される。
  拒否側だけでなく受理側（実行時に解決する種別がパスを省いた綴り）も条件に含める。片側だけでは
  検査が種別のみを見てパスの有無を落とす方向へ縮んでも満たされてしまう。受理する側は、その文書が
  最後まで通ることではなく、この層が判断しない事柄を表す。評価時に絶対パスが決まる種別がパスを
  省いた文書を拒否するのは engine の root 解決の担当であり、条件は責務がそちらにあることまでを含む
- **root の種別が空である文書の拒否** — どの基準へ配置するかが定まらないまま後段へ渡さない
  こと。root オブジェクトを省いた書き方は既定値を経て同じ検査へ落ちるので、独立した保証では
  なく同じ条件の別の綴りとして扱う
- **文書が存在しない場合の失敗** — 配置物に文書が無ければ失敗すること
- **任意フィールド `identity` の復元** — トップレベルの `identity` があればその値を、無ければ空として
  読むこと。値の形は検査しない

版と root の種別を拒否する条件では、エラーが意図した検査の由来であることまで見る。別の検査や
復元の失敗でエラーになっても満たされてしまうと、検査が消えたことを取り逃がす。残る 2 つの
拒否（未知のフィールド・文書の不在）は失敗すること自体までを条件とする。

外部プロセスを起動せず、一時ディレクトリへ文書を直接書き出した fixture に対して評価する。
