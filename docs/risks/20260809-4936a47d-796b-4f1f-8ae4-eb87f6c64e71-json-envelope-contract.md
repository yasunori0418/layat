# RISK-4936a47d-796b-4f1f-8ae4-eb87f6c64e71: --json のエンベロープが niface 規約から外れ機械可読出力の消費側が壊れる

## リスク

`--json` の出力は layat をスクリプトから使う消費側にとっての契約であり、schema から外れた
文書・実行ごとに形の変わる文書を出すと、消費側は自分のパーサが壊れて初めて気づく。壊れ方が
静かなのが厄介で、layat 自身は正常終了したまま不正な文書を渡す。

具体的な壊れ方は 3 系統ある。

- **schema 適合そのものからの逸脱** — エンベロープの必須キー欠落・型違い・item id の導出則
  （identity の JCS を SHA-256）のずれ。id がずれると他実装との相互運用が崩れる
- **subject 数による形の揺れ** — `--all` の 0 件 / 1 件 / 複数件が「長さの違う同じ文書」に
  ならず、件数ごとに別形状になる。とくに 0 件で `results` が消える・1 件で単一実行と
  異なる形になるのは、消費側が件数で分岐せざるを得なくなる
- **エンベロープを出すべき実行で出さない / 出すべきでない実行で出す** — 成立条件を満たさない
  実行（help・completion）まで文書を出す、あるいは失敗経路で文書が欠ける

読み取り系（`--dryrun` / info インベントリ）も同じエンベロープに乗るため、変更系だけを見て
いると読み取り系の形が崩れていることを見落とす。

## 影響

消費側のパーサが壊れる。impact を medium とするのは、破れるのが出力の形であって FS の配置では
なく、エンベロープを規約へ戻したうえでの再実行が正しい文書を返すため。layat 自身は正常終了した
まま不正な文書を渡し、とくに item id の導出則のずれはパースエラーにすらならず値だけが他実装と
食い違う——この沈黙性は本 risk の中心だが、気づいた後の回復可能性は下げない。likelihood を
low に留めるのは、niface の適合チェッカを Go テスト・E2E の双方に置いており、逸脱の大半が
機械的に捕まる構造になっているため（→ TP-d3000054-42d9-4bac-912a-dd3abc38d3e9）。
