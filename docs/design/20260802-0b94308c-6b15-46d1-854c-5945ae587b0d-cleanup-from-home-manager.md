# DSG-0b94308c-6b15-46d1-854c-5945ae587b0d: 配置と cleanup のアルゴリズムは home-manager の linkGeneration / cleanup を範として Go で再実装する

## 設計

engine の配置・stale 除去アルゴリズムは、home-manager の `linkGeneration` /
`cleanup` を**参考にして Go で再実装する**。`home.file` そのものは再利用しない。

「範とする」対象は、世代由来のマニフェストを前世代と diff して消えた entry の
symlink だけを保守的に消すという**アルゴリズムの骨格**であり、実装コードでも
インタフェースでもない。

この選択が実現手段になっているのは次の点。

- **REQ-c1b3ca5f-d2f7-443c-bc4b-b18413ca97b9 が全モジュールに「engine をキックするだけ」を課している**以上、
  home-manager の機構へ委譲する選択肢は最初から取れない。委譲すれば HM 経路だけ
  振る舞いが HM 由来になり、standalone / devShell と二重化する。したがって
  自前実装が前提になり、残る判断は「アルゴリズムをゼロから設計するか、既に
  実運用で枯れた設計を範とするか」になる
- **REQ-16aef46b-7bb8-4ca1-b962-e9f3ed1fd1d2 が要求する保守的 stale 除去の不変条件**（前世代の記録通りを指す
  symlink のみ消し、通常ファイル・非管理 link・copy target には触れない）は、
  まさに home-manager の cleanup が長年扱ってきた問題で、範とする価値がある部分に
  当たる
- **REQ-1be4d678-959c-44d7-a346-44bfd95af56e が定める「前世代マニフェストとの diff → 配置 → コミット」という
  順序**も同じ骨格に載る。layat 固有なのは、前世代の出所を layat 自身の profile に
  統一する点（ホストの `oldGenPath` に依存しない）

再実装であって移植ではないため、`home.file` の内部表現・HM のオプション体系・
activation の作法は持ち込まない。これらを持ち込むと lib / engine が
home-manager へ依存することになり、独立性が崩れる。
