# ADR-45380022-d959-4b22-aa05-5993ac1f3c87: flock は明示実行で wait、hook 実行で skip

- ステータス: 採用
- 日付: 2026-11-01
- 関連: ADR-0021, ADR-0022
- 起点: engine の設計と実行時セマンティクスの確定（2026-06-11〜06-13）。ADR-0006 §「決定」の並行実行・ADR-0013 §2 を書き直した

## 背景

同じ profile への適用が並行すると、配置と世代のコミットが競合する。そのため engine は profile ごとに
ロックを取る。ロックを他のプロセスが持っているときの振る舞いには、相反する 2 つの要求がある。

- ユーザーが明示的に実行した apply は、確実に適用されてほしい。黙ってスキップされると、適用済みだと
  誤解する
- devShell の shellHook はシェルに入るたびに apply を起動する。高い頻度で実行されるので、待ち行列を作ると
  シェルへの入室が詰まる

## 決定

ロックの取り方を起動経路で分ける。明示的に実行した apply / rollback / reset は、ロックを取れるまで待つ。
shellHook から `--no-wait` 付きで起動した apply は、ロックを取れなければ配置をスキップし、stderr に 1 行
通知して、シェルへの入室を止めずに終える。

フラグと待機中・スキップ時の表示は REQ-1c1526b1-59e3-4264-bb7c-65a10a4aa461、reset のロックは
REQ-a8edc58f-4adc-4637-b888-ab8ccc7e73e4 に置く。

## 根拠

明示実行と shellHook では求めるものが違うので、起動経路で分ければ両方を満たせる。どちらの経路かは
テンプレートが shellHook に埋めるフラグで判別するので、engine が呼び出し元を推測しなくて済む。

shellHook がスキップしても安全なのは、ロックを持っている側が同じ manifest を適用しており、適用が冪等で
同じ状態に収束するからだ。スキップを黙って済ませず 1 行通知するのは、適用されなかったことを利用者が
気付けるようにするためである。

## 棄却した代替案

### 全経路でスキップする

明示的な apply も黙ってスキップされ、利用者が適用済みだと誤解する。

### 全経路で待つ

shellHook が高い頻度で待ち行列を作り、devShell への入室が詰まる。

### 短く待ってから、取れなければスキップする

明示的な apply でも、待ち時間を超えればスキップになる。確実に適用したいという要求を満たせない。
