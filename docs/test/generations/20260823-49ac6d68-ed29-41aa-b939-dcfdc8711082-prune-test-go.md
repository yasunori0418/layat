# CASE-49ac6d68-ed29-41aa-b939-dcfdc8711082: prune_test.go — 孤児系列の判定と系列ごとの削除・dryrun / 確認 / lock / 削除段の失敗

## 対象

`internal/engine/prune_test.go`

`Prune`（→ DSG-096dc893-21f4-45e3-9347-986e9275b4d1）を、tmpdir に手で組んだ 2 つの走査基底
（ユーザー state 基底と `SystemDir` へ差し替えた偽の system 基底）に対して駆動する統合レベルの
テスト。判定の入力は backref `.root` と root の実在だけなので、fixture は `Apply` を回さず
ディレクトリとファイルで組む（root が一度も存在しなかった系列を表現するため）。`SystemDir` を
tmpdir へ向けるので、実 `/nix/var/nix/profiles/` には触れない。

## 検証内容

### 判定の正確性（→ TC-bc653f83-70ce-4920-b7cd-9b70a4cd2cae）

- **孤児の削除** — root を消した系列は `<roothash>` ごと消え、配下の `<name>` profile・世代
  リンク・`.pending`・`.root` が残らない
- **世代を持たない系列** — `.pending` だけで世代リンクが無い系列も、`.root` 単独で `<name>` を
  1 つも持たない系列も、root 不在なら同じく削除される
- **生存系列** — root が実在する系列は残り、`Removed` にも `Skipped` にも現れず warning も出ない
- **配置物** — 生存 root の下に置いたファイルは `Prune` の前後で変わらない
- **`.root` を持たない dir** — home / system mode の `<name>` 直キー dir は、両方の基底で
  走査に混ざらない
- **両基底の走査** — state 基底と system 基底それぞれの孤児が同じ実行で削除される
- **基底が無い / 読めない** — 両基底とも不在ならエラーにも warning にもならない。基底のパスに
  通常ファイルを置いて `ReadDir` を ENOTDIR で落とすと、その基底を名指しした warning が出て
  もう一方の基底の処理は続き、系列を名指しできないので `Skipped` には載らない
- **判定不能な backref** — 空・空白のみ・相対パスの 3 条件を独立に駆動し、いずれも系列が残って
  `backref-unreadable` になる。末尾改行付きの絶対パス（engine が書く形）は trim されて通常
  どおり判定される（`root-stat-failed` へ落ちない）
- **root の stat 失敗** — 検索権限を落とした親の下の root は `root-stat-failed` で残る
  （root 実行では誘発できないので `os.Geteuid() == 0` で skip）
- **dangling symlink の root** — 不在として扱われ系列が削除される
- **root がファイル** — 「実在する」側に落ちて残る（種別を見ないことの帰結）
- **系列列挙の失敗** — 系列 dir の読み取り権限を落として `NamesErr` を誘発すると、`Names` が
  nil のまま返っても `.root` 単独系列と混同されず `series-unreadable` で残る（lock 無し削除の
  経路へ落ちない）。同じ基底の健全な孤児系列は変わらず削除される
- **warning** — `Skipped` に入る各ケースで `Warnf` が呼ばれ、その文言が**対象の系列ディレクトリと
  skip 理由を名指ししている**ことまで見る（記録は整形済み文字列。書式文字列だけを記録すると
  全 skip が同一書式を通るため「何か warn されたか」に縮退し、理由や系列を取り違えた実装が通る）。
  基底が読めないケースは基底パスの名指しを見る

### 安全機構（→ TC-a9857bf7-f7f9-41f9-b42c-9993fd16a5e9）

- **dryrun の非破壊性** — FS が一切変わらず、削除予定が `Removed` に入る。lock も取らないので
  dryrun 後に同じ profileDir の lock が取れる。lock 保持中の系列も dryrun では `Removed` に載る
- **確認へ渡る情報** — `Confirm` が受け取る `PruneResult` の全候補が非空の `Root` を持つ。
  受け取った値はポインタのまま保持して `Prune` 復帰後に見る。**preview は戻り値とは別の値**で、
  engine が後から使い回さないことの担保（コピーして見ると、渡したオブジェクトを削除段で
  詰め直す実装を素通りさせる）
- **非同意の中断** — `Confirm` が false なら `Aborted` が立ち、系列 dir だけでなく配下の `<name>` と
  `.root` まで残り、`Removed` は空になる（判定済み候補が「削除した」と読める形で残らない）。
  ここでも preview をポインタで保持し、**`Aborted` が立つのは戻り値の側だけ**で preview には
  立たず、preview の候補は復帰後も残っていることを見る（doc が宣言した契約と 1:1）。
  `Confirm` のエラーは wrap されて返り、削除は行われず、結果は nil で返る（部分結果が無いため）
- **lock 規律** — 系列内の 1 つでも lock が取れなければ系列ごと `locked` で skip + warning
  （他の `<name>` は残る）。取れていた分は解放される。`ErrLocked` 以外の `Acquire` 失敗
  （権限で `open` が落ちる形・root では skip）も同じく `locked`。他の孤児系列は削除される
- **lock の保持区間** — `<name>` を 2 つ持つ系列で「1 つ目が消えて 2 つ目がまだ在る」区間だけを
  狙って別ホルダーが lock を試み、取れないことを見る。削除前に解放する実装はここで落ちる
  （区間を限定しないと、`Prune` が lock を取る前の窓で取れてしまい偽陽性になる）。2 つ目に
  多数のエントリを詰めて `RemoveAll` の所要時間を延ばし区間を観測可能な幅にしたうえで、
  **区間に一度も入れなかった実行は明示的に失敗させる**（「取れなかった」と「見に行けなかった」が
  同じ結果に潰れると、空虚に通る）。lock 取得が成功したときは対象がまだ実在することも確かめる
  （`lock.Acquire` は open → flock の 2 段で、unlink 済み fd への flock は必ず成功するため、
  区間外での取得を「削除中に取れた」と誤報告する）。ポーリングには上限を置きハングさせない。
  **射程は「削除に入る前に解放する」形の実装まで** — 区間の開始を「1 つ目が消えたこと」で
  定義する以上、1 つ目の lock 鍵はその時点で既に無く、「各 `<name>` を自分の `RemoveAll` 直後に
  個別解放する」形はこの検証では押さえられない
- **lock なし削除** — `<name>` を 1 つも持たない `.root` 単独の系列は lock 無しで削除される
- **削除後の解放** — 系列削除後に同じパスを作り直して lock が取れる（fd 上の flock が残らない）
- **削除段の失敗** — 系列 dir を読み書き不可にして「何も消えていない × 権限」を誘発し、
  `permission-denied` で残って他系列の削除が続くことを見る（root では skip）。`<name>` を
  2 つ持つ系列の 2 つ目で権限失敗させた「1 つ以上消した × 権限」はエラーになり、`Skipped` に
  載らず `Removed` にも数えられない（root では skip）。系列直下に stray file を置いて最終
  rmdir を ENOTEMPTY で落とすと、非権限の失敗がエラーで返り `permission-denied` へ丸められない
  （root でも成立する誘発）。**「何も消えていない × 権限以外」に直接対応するケースは持たない** —
  静的 fixture では root-proof に誘発できず、実装へフォールト注入の seam を足さない裁定に従う
  （→ TC-a9857bf7-f7f9-41f9-b42c-9993fd16a5e9 の但し書き）。`!removedAny` 条件を守るのは上の
  権限 2 セルの対
- **`Removed` の正の側** — 失敗より前に完了した系列は `Removed` に残る
- **後続の系列へ進まない** — 失敗した系列より**後にソートされる**健全な孤児系列を fixture へ
  置き、それが削除されず `Removed` にも現れないことを見る。失敗系列が常に最後に処理される
  fixture だけだと、半端に壊れた系列を残したまま後続を削り続ける実装が素通りする。これは
  **ENOTEMPTY 側（root でも成立する誘発）のケースが持つ** — 権限側に置くと root 実行で
  被覆ごと消える（→ TP-deb05610-44bc-4962-8939-952392e5fbd0 の横断規約）
- **`.root` の残存と再実行** — 失敗した系列に `.root` が残り、権限を戻した再実行が同じ系列を
  ふたたび拾って削除する（削除順が `<name>` → `.root` → `<roothash>` であることの担保）
