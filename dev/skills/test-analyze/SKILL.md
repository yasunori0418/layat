# test-analyze: テスト分析（テスト条件の識別・sara 版）

ISTQB/JSTQB のテストプロセス 7 活動のうち **テスト分析（test analysis）** を担う単機能
スキル。テストベース（test basis: 仕様・設計・コード・risk item）を分析して
**「何をテストすべきか」= テスト条件（test condition）** を識別し、成果物を
**test_condition item（1 条件 1 item・`mitigates` で risk へ接続）** として起こす。

型・relation・ID の基盤規約は **sara-docs スキルが正本**。テストケースの導出
（test-design）・実装・実行・レポートは各専用スキルの担当で、ここでは呼び出さない。
「テスト条件（何を確認するか）」を出すのがゴールで、**具体的なテストケース（入力値・
期待結果）の設計はしない**。

## このスキルが従う横断原則

1. **1 ファイル 1 item + 出力先はプロジェクト規約**。test_condition は `docs/test/` 配下
   （サブディレクトリの区分けはプロジェクトの CLAUDE.md 等に従う）。工程固定文書
   （`test-analysis.md` 等）と mini サマリは作らない。
2. **調査優先 + 決定のみ質問**。テスト対象のコード・仕様・既存テスト・入出力・状態遷移は
   利用者に訊く前に自分で調べる。利用者にしか決められない判断（優先度の例外・網羅範囲・
   除外してよい条件）だけを `AskUserQuestion`（推奨案先頭）で確認する。流れは
   **調査 → ドラフト提示 → 承認 → 採番 → 書き込み → `sara check` green**。
3. **前工程の成果物を代作しない**。対象に risk が無ければ `/test-plan` を提案して停止する
   （手順 1）。
4. **単機能の堅持**。後続工程が必要なら `/test-design <テスト対象名>` の実行を提案するに
   留める（代わりにテストケースを設計しない）。
5. **成果物の記述スタイル**。略号・コードネームを定義なしで使わない。スキルの実行記録を
   item に含めない。

## 手順

### 手順 0: テスト対象の確定

- 引数 `<テスト対象名>` があればそれを対象名とする。無ければ利用者に一言で確認する。
- 出力先サブディレクトリ（`docs/test/` 配下の区分）はプロジェクト規約から特定する。

### 手順 1: テストベースの収集（事実収集 + 前工程判定）

原則 2 に従い、以下を**自分で調べる**（利用者に訊かない）:

- **前工程成果物（グラフ走査）**: 対象の REQ / DSG に `threatens` している risk item を
  特定する（`sara query <REQ/DSG のフル ID> -d`。対象周辺の未着手は `sara-gap` の
  unthreatened 一覧がそのまま示す）。risk の評価（likelihood / impact / level）と
  対応する test_plan のアプローチを優先度付けの主根拠にする。
- **仕様・設計**: 対象の REQ / DSG item 本文・`specification`・受け入れ条件。
- **テスト対象のコード**: 入出力・分岐・状態・境界・依存・エラー処理。
- **既存テストと既存 TC**: 何が既にテスト済みか・既存の test_condition が何を束ねているか
  （重複を避け、抜けを見つける）。

**対象の REQ / DSG に threatens する risk が 1 件も無ければ、ここで停止する**。
`/test-plan <テスト対象名>` の実行を提案する（原則 3）。リスク評価なしで条件識別だけ
進める縮退モードは**無い** — test_condition の upstream は `mitigates → risk` のみで、
risk 不在の TC は strict check の orphan error になり構造的に成立しないため。

### 手順 2: テスト条件の識別

テストベースから **テスト条件（test condition）= テストで検証すべき項目・観点** を
洗い出す。「どんな入力値でどう振る舞うべきか」の抽象レベルで挙げる（具体値の設計は
test-design）。**識別した 1 条件 = test_condition item 1 件**。

識別の切り口（テスト対象に応じて使い分ける。全てを埋める必要はない）:

- **機能要求**: 各機能が満たすべき振る舞い・受け入れ条件。
- **入力の区分**: 正常系・異常系・境界・同値クラスに分かれる観点。
- **状態・遷移**: 状態を持つ対象の状態と遷移、禁止遷移。
- **例外・エラー処理**: 失敗経路・タイムアウト・リトライ・ロールバック。
- **非機能**: 性能・セキュリティ・並行性・データ整合性（対象範囲内のもの）。
- **相互作用・依存**: 外部システム・境界インターフェイス・副作用。

トレーサビリティは relation と本文で持つ: 対応するリスクは frontmatter の `mitigates`
（1 本以上）、切り口とテストベース（REQ / DSG・コード箇所）は本文の節へ
（[references/item-sections.md](references/item-sections.md)）。

**粒度ガード（テスト設計へ踏み込まない）**。次の書き方はテストケース設計
（`/test-design`）への踏み込みなので避ける:

1. **同値クラスの列挙**: 入力区分ごとに 1 行ずつ期待挙動を書く（「未設定→X」「空文字→X」…）
   のは同値分割（設計技法）の適用結果。「判定の全区分が仕様どおり解釈されること」の
   1 条件に畳む。
2. **期待結果の埋め込み**: 「◯◯が△△で出力される」のような期待結果文はケース記述。
   「仕様 §X の互換 N 項目を満たすこと」のように仕様参照で束ねる。
3. **検証手段の混入**: golden master 比較・比較対象システムとの値一致など「どう確認するか」
   はテスト条件ではなくテスト計画側のアプローチ。条件から外す。

目安は**機能領域ごとに 1 条件・対象全体で 10 件前後**（あくまで目安。大規模対象で
超えるときは理由を添える）。細分化した区分・期待値は捨てず、**TC item 本文の備考節**へ
書いて `/test-design` のケース導出素材として引き継ぐ。

### 手順 3: 優先度付け

- **TC の優先度はフィールドにしない**。`mitigates` 先 risk の `level` から導出する
  （複数の risk を mitigates するなら最高 level）。これにより優先度の二重管理
  （risk の再評価と TC 側の手動更新のずれ）を構造的に避ける。
- 導出結果と違う優先度で扱いたい例外があるときだけ、TC 本文に根拠付きで記載し、
  `AskUserQuestion` で利用者の決定を取る。
- 網羅範囲・除外してよい条件の判断が利用者依存なら、ここで `AskUserQuestion`
  （推奨案先頭）で確認する。除外した観点は除外理由ごと該当 TC または risk の本文に残す。

### 手順 4: ドラフト提示 → 承認 → 採番 → 書き込み → 検証

1. test_condition 全 item のドラフト（条件・mitigates 先・切り口・テストベース参照）を
   **本文で提示して承認を得る**（原則 2）。
2. 承認後、`sara-new test_condition <slug> docs/test/<対象> -- --description '<1 文の要約>'` で規約ディレクトリへ生成し
   （採番・ファイル名規約の適用と `sara init` の呼び出しまでを一手で行う。`--mitigates` は
   `--` 以降で渡す）、本文を書き足す（手順は sara-docs の references/sara-cli.md）。
3. `sara check` を回して green を確認する。
4. 末尾で `/test-design <テスト対象名>` の実行を提案する（原則 4）。自分では進めない。

### 手順 5: 仕様の穴の反映（early testing 原則）

分析中に見つけた仕様の矛盾・曖昧さ・抜けている要求・観測不能な状態・テスト困難な構造は、
セクションに書き溜めず test-plan スキルと同じ運用で処理する:

- 利用者の決定で解決できるものは `AskUserQuestion` で決定を取り、**REQ / DSG item へ
  直接反映する**。
- この工程で決められない未決課題は GitHub Issue への起票を提案する。
- スキル自身がテスト対象のコードを修正しない。

### 手順 6: 終了条件の確認と完了宣言

テスト分析の終了条件（exit criteria）。**利用者に「終わりか」と訊かれる前に、スキル側で
判定して宣言する**:

1. test_condition item が識別・書き込み済みで、各 item が `mitigates` を 1 本以上持ち、
   粒度ガードを満たしている（手順 2）。
2. 優先度が risk level からの導出で説明でき、例外には根拠と利用者決定がある（手順 3）。
3. `sara check` が green。
4. 利用者判断（網羅範囲・除外条件・優先度例外）が `AskUserQuestion` で確認済み。
5. 仕様の穴が REQ / DSG への反映または Issue 起票の提案まで処理済み（手順 5）。

全て満たしたら**「テスト分析は完了」と明言**し、`/test-design <テスト対象名>` の提案で
閉じる。満たしていない項目があれば、何が残っているかを列挙して先へ進めない。

## 用語（JSTQB 訳語 / 初出英語併記）

- テスト分析（test analysis）: テストベースを分析して「何をテストすべきか」を識別する活動。
- テストベース（test basis）: テスト条件を導く基となる情報（仕様・設計・コード・リスク等）。
- テスト条件（test condition）: テストで検証すべき項目・観点（具体値ではない抽象レベル）。
  実務で通りの良い「テスト観点」は本スキルでは同義。
- トレーサビリティ（traceability）: テスト条件とテストベース（要求・リスク）の対応関係。
  sara 版では relation（mitigates / threatens）と本文参照が担う。
