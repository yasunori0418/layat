# ADR-0053: 採番責務を sara init へ再配置し、ID をフル UUID へ統一する — 8 文字二層構成の廃止・ADR 連番の維持

- ステータス: 採用
- 日付: 2026-08-17
- 関連: ADR-0048, GitHub Issue #366, #364, PR #363
- 改訂対象: ADR-0048 §4（UUIDv4 二層構成の廃止・`sara-id` による採番の廃止。ADR の連番維持は不変）
- 起点: epic #364 の着手前 grilling（2026-08-17）で確定

## 背景

ADR-0048 §4 は ID を **UUIDv4 の二層構成**と定めた。正式 ID はフル UUIDv4、人間が触る面
（ファイル名・散文中の参照）は前方 8 文字の省略形を使う。当時の sara（0.9.x）は `id_format` を
検証も採番もせず、`sara init` の `suggest_next_id` は連番前提だったため、採番は devShell 同梱の
`sara-id`（`uuidgen -r` + 8 文字 prefix の重複チェック）が担った。

sara 0.10.0 の breaking change `feat!: drive identifier generation from id_format templates` により
`id_format` が採番・補完・検証を駆動する SSOT になり、`sara init` が `{prefix}-{uuid4}` から
UUIDv4 を採番するようになった。PR #363 はこの追従を行い、ADR-0048 §4 の「`sara init` の自動採番は
使えない」という前提の失効を追記したが、**廃止判断そのものは PR のスコープ外**として保留した。
その時点の結論は「`sara-id` は廃止しない」で、根拠は sara の採番が 8 文字 prefix の重複を
見ないことだった（`{seq}` を含まない format では `suggest_next_id` がグラフを参照せず即
`render` を返し、`render` は `Uuid::new_v4()` を素で呼ぶ）。

この保留は「二層構成を続ける」を暗黙の前提に置いている。二層構成をやめれば 8 文字 prefix の
一意性という要件自体が消え、`sara-id` が sara init に対して持つ優位も同時に消える。本 ADR は
その前提を含めて再検討した結果を記録する。

同時に、ADR-0048 §4 が ADR だけ連番のまま残した判断も再検討した。ADR は 47 → 52 本に増え、
epic 単位の並列レーン運用が常態化しており、「最大値 + 1 を手で採る」手順は複数レーンが同時に
採ると衝突する構造を持ち続けている。

## 決定

### 1. 前方 8 文字の二層構成を廃止し、ファイル名・散文参照ともフル UUID へ統一する

ADR-0048 §4 の 3 行表のうち、正式 ID の行だけを残して他の 2 行を書き換える。

| 用途 | 形式 | 例 |
|---|---|---|
| 正式 ID（frontmatter `id:`・relation リスト） | `<PREFIX>-<フル UUIDv4>` | `REQ-8521e8f8-99cc-47f0-b7d0-70c24c837612` |
| ファイル名 | `<YYYYMMDD>-<フル UUIDv4>-<slug>.md` | `20260801-8521e8f8-99cc-47f0-b7d0-70c24c837612-lock-ordering.md` |
| 散文中の参照 | `<PREFIX>-<フル UUIDv4>` | `REQ-8521e8f8-99cc-47f0-b7d0-70c24c837612` |

ファイル名が長くなることは受け入れ、**ディレクトリ分割による短縮はしない**。UUID の
先頭 2 文字でディレクトリを切る等の案は、item 型ごとのフラットな一覧性（`ls docs/requirements/`
で全件が読める）を失う代償のほうが大きい。

散文・frontmatter での **8 文字省略形の参照は禁止**する。省略形はフル ID の前方一致であるため
`grep` は通るが、参照先が一意に定まらない層を残すこと自体が二層構成の本体であり、片方だけ残す
意味が無い。

### 2. 省略形禁止は CI の機械検査ではなく、生成の機械化と全面移行で担保する

禁止を破る経路は「人が手でファイルを作る」「人が散文へ手で書く」の 2 つ。前者は起票ラッパー
（→ 決定 3）に寄せることで塞ぐ。後者は既存 332 item の全面移行（ファイル名・散文とも）により、
リポジトリ内に模倣すべき省略形の実例を残さないことで塞ぐ。

**残余リスクを明記する**: 散文は自由記述であり、厳密には構造保証の外にある。移行後に誰かが
`REQ-8521e8f8` と手で書いても、それはフル ID の前方一致なので `sara check` は検出しない
（sara は散文中の ID 参照を見ない）。本 ADR はこのリスクを受容する。CI 検査を持たない理由は
「棄却した代替案」の「省略形の禁止を CI で機械検査する」に記す。

### 3. `sara-id` を完全廃止し、後継として `sara init` を包む起票ラッパーを新設する

`sara-id` は ID を 3 形式（`id:` / `filename:` / `ref:`）で標準出力へ印字するだけで、item ファイル
自体は作らない（生成は元から `sara init` の担当）。その 5 つの機能の行き先は次のとおり。

| `sara-id` の機能 | 廃止後の行き先 |
|---|---|
| フル UUIDv4 の採番 | `sara init` が行う（0.10.0 以降） |
| 8 文字 prefix の重複チェック | **不要**（決定 1 で二層構成を廃止したため） |
| 散文参照用の省略形（`ref:`）の出力 | **不要**（同上） |
| 型名・別名 → prefix の写像解決 | **不要**（`sara init <型名>` が型名を直接取る。`docs/model.yaml` との双方向一致検査もろとも消える） |
| ファイル名素材（`<日付>-<ID>-<slug>`）の組み立て | 後継の起票ラッパーが引き継ぐ |

残るのはファイル名素材の組み立てだけである。これを `sara init` の呼び出しへ前後から被せる薄い
ラッパー（`sara-new`）へ寄せ、`sara-id` は撤去する。採番ロジックを自前で二重持ちしない形に
することが眼目で、**ラッパー自身は ID を生成しない**。

ラッパーは `dev/scripts/` の独立ファイルとして置く（devShell 定義へ埋め込まず、他プロジェクトへ
横展開しやすい形にするため）。**契約テストは持つが test_plan は起こさない** — `sara-id` が
TP-d7da4065-ce7c-4a0b-be49-5108256e177a を持っていたのは二層構成の一意性保証という規範を負っていたからで、規範を持たない
ファイル名の組み立てだけの薄いラッパーに逆算階層は要らない。

### 4. ADR は連番を維持し、採番は `sara init` へ委譲する

ADR-0048 §4 の「ADR のみ連番を維持する」は**不変**。ただし採番の手順を、`docs/adr/` の最大値を
人が読んで + 1 する運用から、`sara init adr` への委譲へ改める。`model.yaml` の
`{prefix}-{seq:04}` は 0.10.0 でも有効で、`suggest_next_id` は `{seq}` があればグラフを走査して
最大値 + 1 を返す（本 ADR の番号がその初適用）。

並列レーンでの同時採番は**防げない**。`suggest_next_id` は自分のワークツリーのグラフしか
見ないため、2 レーンが同時に `sara init adr` を呼べば同じ番号を採る。これはマージ後の
`sara check` の `DuplicatesRule`（フル ID の完全重複 = Error）が検出する。採番時の防止では
なく事後検出で受ける、という分担を明示的に選ぶ。

### 5. sara 0.10.0 の未追跡 breaking change 4 件は本リポジトリへ影響しない

epic #364 が前提として挙げた 4 件を調査した結果は次のとおり。

| breaking change | 影響 |
|---|---|
| `warn instead of blocking when no parent item exists` | 対話 `init` のみの変更。`sara check` は無変更で、`strict_mode = true` による orphan の Error 昇格も従来どおり |
| `surface skipped files in sara diff` | 本リポジトリは `sara diff` 未使用 |
| `fail the diff instead of comparing the working tree with itself` | 同上 |
| `reject an identifier already used` | `init` 時にフル ID の重複を拒否する。決定 4 の事後検出を前倒しできる方向の変更で有益 |

## 根拠

### なぜ二層構成をやめるのか

二層構成は「フル UUID は人が読めない」という前提への対処だった。実運用の 332 item を経て、
人が ID を読む場面が想定より少ないことが分かった。item を辿るのは `sara query` であり、
散文中の参照からフル ID を得る手順（8 文字で `rg` して宣言側を引く）は CLAUDE.md に手順として
書かねばならないほどの摩擦を生んでいる。省略形の可読性が買っているものは、この摩擦と
「参照が一意に定まらない層」の保守コストに見合わない。

決定的なのは、二層構成が **sara の関知しない層**にあることである。sara は正式 ID の一意性しか
見ない。8 文字 prefix の一意性を保つには自前の採番コマンドが要り、その契約テストが要り
（TP-d7da4065-ce7c-4a0b-be49-5108256e177a）、モデル定義との prefix 写像の双方向一致検査が要る。この一式は全て
「sara が見ない層を人手で保証する」ためのものである。層を消せば一式ごと消える。

### なぜ ADR だけ連番を残すのか

移行の破壊範囲を実測した。リポジトリ内の散文言及 2006 件と Issue / PR 本文 968 件・コメント
115 件は機械置換できる（Issue / PR は `gh` で編集可能であることを実測した）。しかし
**コミットメッセージ 306 件は編集不能**である。履歴を書き換えずに連番言及を消す手段が無い以上、
移行しても連番 → UUID のエイリアス表を恒久的に持ち続けることになり、「二重の ID 空間を無くす」
という移行の便益がそのまま消える。

一方で連番を残す側のコストは小さい。ADR は 52 本を数えて採番衝突の実績がゼロで、ニアミスも
確認されなかった。並列レーンでの衝突リスクは残るが、決定 4 のとおり `sara check` が事後検出
する。検出後の手戻り（番号の振り直しと参照の書き換え）は、ADR 1 本の相互参照の範囲に収まる。

### なぜ採番を `sara init` へ委譲するのか

「最大値 + 1 を人が読んで採る」手順は、衝突を防げないうえに読み間違いを許す。実際、本 ADR の
起票時に epic #364 の本文が想定した番号（ADR-0054）と実際の最大値 + 1（ADR-0053）が食い違った。
既存最大を ADR-0053 と誤認していたためで、これは人が数える手順の失敗そのものである。委譲すれば
少なくとも「現在のワークツリーの最大値 + 1」であることは機械が保証する。

## 影響

- ADR-0048 §4 の二層構成は失効する（同 ADR 側に改訂注記を追記する）。§4 の「ADR のみ連番を
  維持する」だけが生き残り、その採番手順が本 ADR で変わる
- `docs/adr/README.md` と CLAUDE.md の ADR 採番手順（「最大値 + 1 を手で採る」）を
  `sara init adr` への委譲へ改める
- 既存 332 item のファイル名改名と散文約 1700 件の省略形展開が必要になる（別 issue）
- Issue / PR 本文に残る旧ファイルパスのリンク切れは**許容する**。8 文字の言及はフル UUID の
  前方一致なので、`grep` による解決性は移行後も残る
- **ID 規約の一次所在**である `docs/model.yaml` 冒頭の「ID 形式（UUIDv4 二層構成）」節と、
  `adr` 型の `id_format` コメント（「既存 47 本」の旧記述を含む）を書き換える（別 issue）。
  ADR-0048 の 2026-08-16 追記が規範の所在をこの節へ移しているため、ここが最優先の追随対象になる
- CLAUDE.md も同じ移行で書き換える（本 ADR では ADR 採番手順だけを先行して直した）。対象は
  「ID 規約（UUIDv4 二層構成）」表と、「規約」節に残る `sara-id` 採番の言及の 2 箇所
- `sara-id`・`dev/tests/sara-id.sh`・`checks.sara-id` と TP-d7da4065-ce7c-4a0b-be49-5108256e177a が撤去の対象になる（別 issue）。
  **TP を消すときは参照元 3 箇所も同時に落とす** — ADR-0048 の `justifies`（残る INF-659b139d-0cf8-4c65-b30d-93c5ee2dfc71 が
  1 本あるので削除しても orphan にはならないが、消し忘れると `Broken reference` で `sara check`
  が落ちる）、`docs/spec.md` の test_plan 索引行、CLAUDE.md の「テスト系 item の粒度」節
  （`dev/tests/sara-id.sh` は TP-d7da4065-ce7c-4a0b-be49-5108256e177a のみを持つ、という区分外の記述）。**最後の 1 つは
  `sara check` も `test-doc-map.sh` も見ない**ので、取りこぼすと機械検出なしに stale で残る
- INF-659b139d-0cf8-4c65-b30d-93c5ee2dfc71 側の追随は 2 系統に分かれる。片方だけ直すともう片方が旧記述で残る。
  - **構成節**: `sara-id` 行・`dev/tests/sara-id.sh` 行（内訳は `dev/tests/*.sh` の各行が担う）と、
    `sara` ジョブ行の件数。件数は**表の直下の散文にも同じ数字が出る**ので両方直す。なお件数は
    現時点で既に stale で（`sara-gap` の追加が反映されず「3 件」のまま。実 CI は 4 件）、
    **撤去と新設で件数自体は変わらない**ため、旧数値からの引き算ではなく実 CI のステップに
    合わせて数え直す（欠落している `sara-gap.sh` 行の補完も併せて）
  - **「ID 規約」節**: 二層構成と ADR 連番の規約
- 起票ラッパーの契約テストを CI へ載せる（別 issue）。`sara-id.sh` の撤去と対になる追加で、
  撤去だけを実施すると契約テストが CI から落ちる。対になるのは `sara` ジョブのステップと
  `checks.*` だけではなく、**`dev/scripts/test-inventory.sh` の `FLAKE_CHECKS`（check をハード
  コードで列挙している）と `dev/tests/test-doc-exclusions.tsv` の除外行**を含む 4 箇所。除外行を
  差し替えないと `test-doc-map.sh` が stale な除外または CASE 無しのテスト資産として落ちる。
  除外理由は現行の `sara-id` 行（「TP-d7da4065-ce7c-4a0b-be49-5108256e177a のみを持ち」）を流用できない — 決定 3 で後継は
  test_plan を起こさないと決めたため、`sara-gap` 行と同型の理由文になる。その `sara-gap` 行は
  理由文の末尾で `sara-id` を名指ししている（「sara-id と同じ扱い」）ので、参照先が消えないよう
  併せて直す
- **`sara-id.sh` を根拠として名指しする散文が兄弟スクリプトに残る**（`dev/tests/sara-gap.sh`・
  `test-doc-map.sh`・`risk-matrix.sh` のコメントに「`-e` は使わない（sara-id.sh と同じ理由）」
  「sara-id.sh §6b と同じ扱い」等が計 7 箇所）。撤去すると根拠の参照先が消える。除外行と同じく
  機械検出に載らないので、撤去 issue が明示的に拾う
- 起票ラッパーの新設に伴い、エージェント向けの起票手順が更新される（別 issue）。対象は
  `dev/skills/sara-docs/`（`SKILL.md` の「ID 規約」節と `references/sara-cli.md` の
  「ID は先に `sara-id` で採番し `--id` で渡す」手順）・`dev/skills/test-plan/`・
  `dev/skills/test-analyze/`。`docs/agents/` には採番・起票手順の記述は無い

## 棄却した代替案

### 二層構成を続け、`sara-id` の責務を採番から重複チェックへ寄せる

epic #364 が最初に挙げた折衷案。`sara init` が採番し、8 文字 prefix の重複は別途検査する分担に
すれば、採番ロジックの二重持ちは消える。採らないのは、**二層構成そのものの便益が小さい**と
判断したため（→「なぜ二層構成をやめるのか」）。この案は自前実装の量を減らすが、sara の関知
しない層を保守し続ける構造は変えない。層を消すほうが得られるものが大きい。

### 8 文字重複チェックを事後検査（CI）へ移す

同じく epic #364 の案。採番を `sara init` へ一本化し、`docs/` 全体の 8 文字一意性を CI で検査
する。これも二層構成の存続が前提であり、上と同じ理由で採らない。加えて、衝突時の手戻り
（採番し直し + 参照の全書き換え）が事後になるぶん高くつく。

### ADR も UUID へ移行する

ADR-0048 §4 が一度棄却した案の再検討。当時の棄却理由（相互参照・README 運用・Issue 言及が
連番前提）のうち Issue / PR 本文は `gh` で編集可能と実測できたが、**コミットメッセージ 306 件が
編集不能**である点は解けない。エイリアス表の恒久管理から逃げられず、移行の便益が残らない
（→「なぜ ADR だけ連番を残すのか」）。棄却は維持する。

### 省略形の禁止を CI で機械検査する

`docs/` の散文を走査し、フル UUID の前方一致となる 8 文字パターンを検出して落とす検査。
採らない理由は 2 つ。第一に、**正しい参照の途中経過を誤検出する**。フル UUID を書いた行も
先頭 8 文字を含むため、「8 文字の直後がハイフン + 続きの UUID でない」という否定形の判定が要り、
Markdown のリンク・コードブロック・表の折り返しで壊れる。第二に、**移行後の再発は構造的に
起きにくい**。ファイル生成が機械化され、リポジトリ内に模倣すべき省略形の実例が 1 つも残らない
状態では、人が省略形を新たに発明する経路が実質的に無い。検査の維持コストが、防ぐリスクに
見合わない（残余リスクは決定 2 に明記した）。

### 並列レーンの ADR 採番衝突を採番時に防ぐ

`sara init adr` の呼び出し前に origin の最新を取得して最大値を求める、ロックを持つ、等の案。
採らない。レーンは独立したワークツリーで動き、採番時点で他レーンの未 push な採番は原理的に
見えない。防止を謳う仕組みは「防げていない場合がある」ぶん事後検出より危険で、`sara check` の
`DuplicatesRule` がマージ後に確実に検出する以上、二重の仕組みを持つ必要が無い。
