# ADR-993423c8-6374-4b72-aa2d-5d5fdbe7a3e4: ドキュメントサイトのソースを同じリポジトリの site/ に置く

- ステータス: 採用
- 日付: 2026-11-03
- 関連: GitHub Issue #57, `docs/publication-roadmap.md`
- 起点: Issue #57 のサイト設計。ADR-0037 §1 を書き直した

## 背景

publication-roadmap は、静的サイトジェネレータによるドキュメントサイトを構想として挙げていた。
nixdoc と gomarkdoc で抽出したリファレンスと手書きのガイドを集め、英語と日本語の両方で出す。
ただ、サイトのソースをどこに置くか、何を載せるかは決まっていなかった。

## 決定

ドキュメントサイトは Astro（Starlight）のプロジェクトとして、本リポジトリの `site/` に置く。
載せるのは利用者向けの usage ガイドと API リファレンス（英日）で、設計根拠のドキュメント（ADR・
`CONTEXT.md`・`docs/spec.md`・`docs/design.md`）はリポジトリ内に留めてサイトには載せない。

構成の細目は INF-0865477b-21b2-4feb-9c06-1a882a4e595a に置く。

## 根拠

リファレンスの抽出元（`lib/` の doc-comment と Go のソース）とサイトが同じリポジトリにあれば、
API の変更とドキュメントの更新が同じ PR で一緒に進む。リポジトリが膨らむ懸念は、`site/` への
隔離と、devShell や CI ジョブを分けたビルドで抑えられる。

設計根拠のドキュメントは日本語で書いており、リポジトリを読む人に向けたものである。サイトの
読者は利用者で、対象が違う。

## 棄却した代替案

### 別リポジトリ（`layat-docs`）に置く

本体のリポジトリは軽く保てる。ただ、API の変更と抽出結果の更新が別々に進む。サイトが古い
リファレンスを配信し続けやすくなり、その危険のほうが大きい。

### 設計ドキュメントもサイトに載せる

日本語のまま載せると英日両方で出す方針に合わず、翻訳すると維持の負担が大きすぎる。
