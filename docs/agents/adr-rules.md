# ADR の規則

ADR（Architecture Decision Record）の粒度・ステータス・ADR 間の関係・item への接続についての
汎用の規則。特定のリポジトリへの当てはめ（frontmatter の対応表・採番の手順・実例）は各リポジトリの
ADR ディレクトリの README が持つ。

## 粒度: 1 本に 1 つの決定

1 本の ADR には、**単独で覆せる 1 つの決定**だけを書く。

判定の問いは「この決定だけを覆したとき、同じ ADR の他の決定はそのまま残るか」。残るなら別の
決定なので、ADR を分ける。逆に、片方を覆すともう片方が意味を失う決定どうしは 1 つの決定として
1 本にまとめる。

- タイトルは 1 つの動詞句にする。「／」「と」「・」で主題を並べたタイトルは、複数の決定を
  抱えている兆候になる
- `justifies` の本数が多いこと（目安 8 本以上）は分割を考えるきっかけにする。規則ではないので、
  1 つの決定が多くの item を決めているなら分けない

## 本文の構成

本文は **背景・決定・根拠・棄却した代替案** の 4 節を持つ。規範の細目（入力・出力・エラー・境界
条件など）は ADR に書き下さず、要求や設計の item に書いて `justifies` で指す。ADR は「なぜその
規範にしたか」を残す場所で、規範の正本ではない。

検討して棄却した代替案は、その ADR の「棄却した代替案」節に残す。棄却だけを独立した ADR に
するのは、棄却に独自の起点（提案の Issue や議論）があるときに限る。

## ステータス

| ステータス | 意味 |
|---|---|
| `提案` | 検討中で、まだ決定していない |
| `採用` | 決定として有効 |
| `不採用` | 提案を棄却した決定の記録。棄却したという決定が有効なので、ADR 自体は有効 |
| `廃止` | 後継の ADR に置き換えられ、もう有効ではない |

`不採用` と `廃止` を混同しない。`不採用` は「やらない」という決定がいまも有効な ADR で、
`廃止` は決定そのものが後継に置き換わった ADR。

## 改訂は丸ごとの置き換えで表す

既存の ADR の決定を 1 つでも変えるときは、その ADR を部分的に書き換えず、**丸ごと新しい ADR として
書き直し、古い ADR を `廃止` にする**。節単位の部分改訂を表す関係や、古い ADR への改訂注記は使わない。
部分改訂を積み重ねると、古い ADR のどこが生きているかを読者が注記から再構成しなければならなくなるため。

- `supersedes` は文書丸ごとの失効だけを表す。後継の ADR から置き換えた ADR へ張る
- `supersedes` で指された ADR は `廃止` にする。`廃止` の ADR は 1 本以上の `supersedes` から指される。
  この対応は frontmatter だけで機械的に確かめる
- 改訂を伴わない参照は `references` で表す。`supersedes` とは併用しない

### 廃止にできる条件

古い ADR を `廃止` にできるのは、**古い ADR の全決定に後継が揃ったとき**だけ。後継は、新しく起こした
ADR か、別の有効な ADR に既にある決定のどちらでもよい。

1 本の古い ADR を複数の新しい ADR へ分けて書き直す途中では、新しい ADR の `origin` に元の ADR と節を
書くにとどめ、`supersedes` はまだ張らない。最後の決定に後継が揃い、古い ADR を `廃止` にする変更の
中で、全ての後継から `supersedes` をまとめて張る。

### 廃止した ADR に残すもの

`廃止` にした ADR は、本文も既存の注記も原文のまま残す。変えるのは次の 3 つだけ。

- 本文のステータス行
- frontmatter の `status`
- 冒頭に置く後継の一覧（どの決定がどの ADR に移ったかを示すバナー）

`justifies` も外さない。要求や設計の item の出典が古い ADR を指していても、その参照は経緯として
そのまま有効になる。

## 統合と分割の手順

複数の決定を抱えた ADR や、改訂を重ねた ADR を書き直すときの手順。

1. 古い ADR の決定を棚卸しする。決定ごとに、いまも有効か・後の ADR が改訂したか・撤回されたかを
   分類する
2. 撤回された決定には新しい ADR を起こさない。完了した一回限りのプロセス決定も同じ。それ以外の
   有効な決定は、価値が低く見えても省略せず 1 決定 1 本で起こす
3. 改訂された決定は、改訂後の内容を現時点の決定として書く。改訂の経緯は書かず、背景と根拠だけを書く
4. 新しい ADR の `justifies` は、古い ADR の `justifies` から当該決定に対応する item だけを引き継ぐ
5. 古い ADR の全決定に後継が揃ったら、`supersedes` を張って古い ADR を `廃止` にする

## `justifies` の選定基準

**`justifies` は必須**で、ADR が決めた item を 1 本以上張る。空の `justifies` を埋め忘れとして
機械判定できる状態を保つため、空のまま出さない。張る先の item がまだ無ければ、ADR と同じ変更の中で
item を起こしてから張る。決定を item に落とせない ADR は、決定が定まっていないか粒度が大きすぎる
ので、先にそちらを解く。

どの item を張るかの基準は「**その ADR が、その item の規範の形成に実質的に寄与したか**」。決定の
実体である ADR 1 本だけが張るのではなく、寄与した ADR が複数あれば全てが張ってよい。

次の 2 つは寄与が成立しないので張らない。

1. **接続先の item 自身が、`justifies` を受けない理由を本文に明記している**。ただし「その規範を
   この item には含めない」という宣言と「その ADR に依拠していない」ことは別なので、文面を読んで
   判定する
2. **ADR がその規範を決めていない**。背景で既存の前提として言及するだけの ADR は張らない

### 網羅性の監査

張り先の候補は 2 方向から挙げる。

- ADR の決定節を上から順に読み、規範ごとに張り先を探す
- item の出典節が「〜はこの ADR が定めている」と名指ししている ADR から引く。名指しの無い item も
  あるので、こちらだけでは拾い切れない

挙げた候補は、**ADR の決定節に、その item の規範そのものを決めた決定文があるか**で絞る。出典節の
名指しは周辺規範の淵源も含むので、名指しがあることは寄与の証明にならない。次の 2 類型は原則として
張らない。

- item の本文が、その規範を別の item へ委譲しているもの。委譲先に同じ ADR が張られていれば寄与は
  回収済み。ただし item の規範文そのものが、その ADR の決めた規範を対称化・拡張の対象として直に
  述べているときは張る。他の item を経由した参照はこれに当たらない。判定材料は本文の注記ではなく
  規範文に置く
- 「淵源」「姿勢」といった態度の供給元としてだけ挙がるもの。語で判定せず、決定節に対応する
  決定文があるかで見る

網羅性はグラフの検証では判定できない。検証が見るのは「1 本以上張ってあるか」だけで、「決めた規範を
全て張っているか」は見ない。新しい ADR を書いたら、決定節を上から順に見て規範ごとに張り先を確かめる。

## 採番

ADR も他の item と同じく UUID で採番する。連番は並列の作業で同じ番号を取り合い、マージ後に
採り直しが要る。UUID ならこの衝突が構造的に起きない。
