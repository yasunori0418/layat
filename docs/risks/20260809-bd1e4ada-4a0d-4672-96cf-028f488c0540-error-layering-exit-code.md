# RISK-bd1e4ada-4a0d-4672-96cf-028f488c0540: 失敗の帰属層と終了コードがずれ部分失敗の成否判定を誤らせる

## リスク

失敗の表現には「誰がその失敗を持つか」という層の選択があり、層を誤ると消費側は失敗の原因を
取り違える。entry スコープの失敗（配置先の衝突など）は当該 item が持つべきで、主体そのものが
成立しなかった失敗（config の評価・ビルドの失敗）は subject が持つべきで、主体が確立する前の
失敗はトップレベルが持つべきである。同じ失敗を 2 つの層に重複して載せると、消費側は失敗件数を
二重に数える。

`--all` の部分失敗はこの層構造が最も崩れやすい。1 つの config の失敗が兄弟 config の
ステータスやインベントリを汚す、失敗した config 以降が subject として現れず「実行されな
かった」と「成功した」が区別できなくなる、といった形で崩れる。

終了コードはこれと対になる。エラー（1）と dryrun の conflict（2）が同時に起きたときにどちらを
返すかは単なる数値の最大でも最小でもなく、優先順位の決めごとであり、実装が素朴に最大値を
取ると conflict がエラーを覆い隠す。加えて、try-lock でスキップされた主体を失敗として数えると、
何も失敗していない実行が失敗として報告される。

エラーコードの分類も同じ性質を持つ。原因ごとのコード（ビルド失敗・IO・ロック・一般失敗）が
ラップを越えて生き残らないと、消費側は原因で分岐できず全てを汎用エラーとして扱うことになる。

## 影響

自動化された呼び出し側が成否を誤判定する。部分失敗を成功と読む、あるいは成功した config の
結果まで失敗として捨てる。impact を medium とするのは、誤るのは失敗の表現であって FS の配置
そのものではなく、層と終了コードの割り当てを直したうえでの再実行が正しい判定を返すため。
部分失敗を成功と読む方向の誤りでは、CI もスクリプトも成功と判断してそのまま先へ進み、
破損した配置が残っていることに誰も気づかない。この沈黙性は本 risk の中心だが、その配置自体は
原因を直した再 apply で収束する（収束しない側は RISK-68e810c5-4e68-4b25-9bc0-6b2613022b49 が持つ）。

likelihood を medium とするのは、失敗の帰属層は TC-733ac4ed-dac3-4bb8-9bfd-fd1cbdc300c9 が、終了コードの集約は
TC-ddee6cc4-bc10-4107-bc7e-288a5fb62f1f が覆っている一方、両者が `--all` の部分失敗という組み合わせで交差し、主体を
1 つ足すたびに層の選択と優先順位を再判断する必要があるため。
